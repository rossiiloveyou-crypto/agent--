# AD · 并行并入清单

> **唯一一份，跨并行分支累积。** 一行一个 workspace，编号 `AD-nn`。
> **谁写**：执行者（在自己的 Phase 完成后追加一行）
> **谁读**：撰写者（并入时按行执行）
> **谁搬运**：人（把本文件拖给撰写者）
> 
> **规范依据**：`../methodology/BLUEPRINT-撰写规范.md` §6.3（并行模式）。
> **它不是什么**：不是完成报告。完成报告（`PHASE-<n>-完成报告.md`）在并入**之后**才进 `task-*/`；
> 本文件只回答一个问题：**「这个 workspace 里的东西，怎么安全地搬到主仓去」**。

|---|---|---|---|---|---|---|---|---|
| AD-01 | P<n> | `<任务名>-PHASE<n>-Workspace` | `<短哈希>` | `<src/x.ts>（改 N 行）、<test/x.test.ts>（新增）` | 新增 N / 删除 N | `suites=<局部值>`、`cases=<局部值>` | BASE-02 ⬜ | ⬜ 未并入 |

> 状态取值：⬜ 未并入 / 🔄 并入中 / ✅ 已并入 / ❌ 并入失败（附原因）/ 🚫 已放弃（附原因）
> 
> 🔴 **「局部实测」栏只是记录，不是基线。** workspace 里测出的数**不许**写回主仓的 `BASELINE.txt`
> —— 两个 Phase 各加了测试，各自只能看见自己那一半（规范 §6.3.5）。

## 三、并入步骤（撰写者填，每个 workspace 一段）

### AD-01 · P<n>

1. **前置**：主仓 `BASE-01` 自洽 / `BASE-02` 新鲜度通过；工作区干净（`git status --porcelain` 无输出）
2. **搬运方式**（二选一，写清用了哪个）：
   - patch：`git diff --binary <基于head>..<workspace head> > ../concurrent/AD-01.patch` → `git apply`
   - 逐文件：`cp` 覆盖，逐个列出
3. **冲突处置**：哪个文件、采用哪侧、为什么
4. 🔴 **合入后重测（硬步骤，不可跳）**：`pnpm test` → 期望 `suites ≥ <合入前主仓值> + <本增量>`
5. **更新 `BASELINE.txt`**（新 `head` / 新数字）→ 触发 **T2** → 旧值进总蓝图 §9.2
6. **更新总蓝图** §四 Phase 状态、§9.1 判据台账（若有修正）
7. **清理**：`git worktree remove <路径>`、`git worktree prune`、删除 workspace 目录

## 四、并行期间的红线（执行者必读）

| 红线 | 为什么 |
|---|---|
| ❌ **不许改 workspace 里的 `BASELINE.txt`** | 合入后主仓基线会被改成「只看一半」的数（§6.3.5） |
| ❌ **不许自己去并入主仓** | 并行隔离的全部价值在于「执行者不碰主仓」；并入是撰写者的事 |
| ❌ **不许改 `task-*/` 下的任何文件** | 那些是主仓侧的文档；完成报告先在 workspace 里写，并入后由撰写者搬 |
| ❌ **不许用 junction 装包** | junction 写穿透，会把主仓依赖改掉（§6.3.4） |
| ✅ **必须**在完成时追加一行 AD-nn | 没有这一行，撰写者不知道要并入什么 |
| ✅ **必须**记录「基于 head」 | 否则无法生成 patch、也无法判断主仓走了多远 |
