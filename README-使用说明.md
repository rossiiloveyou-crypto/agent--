# 蓝图规范包 · 使用说明

> **这是什么**：一套"让 AI agent 写出可执行蓝图"的方法论。**规范本体 + 分级经验库 + 回写机制 + 一套真实范例 + 出处存档。**
> **怎么用**：把 **`methodology\`** 整个文件夹丢给 AI，让它读。就这么简单。
> **目录已分离**：`methodology\`（跨任务复用）与 `task-<任务名>\`（本次任务专属）**互不污染**。

| 目录 | 给谁 | 分享时 |

## 二、怎么用（一句话版）

**把 `methodology\` 整个文件夹拖给 AI，然后说**：

```
这个文件夹里是一套写蓝图用的规范与经验库。
请先读 _先读这份-READ-FIRST.md，按里面的"最小必读集"决定读哪几份，
读完告诉我你理解了、并复述你打算怎么做，我再给你任务。
```

AI 会自动只读该读的**2–3 份**（约 1.5–2 万 token），不会去啃另外几份大的。
想要更精确的开场话术，用 **`投喂说明-先读我.md`** 里第二节的完整版——
它包含"先确认任务类型再动手""引用经验要用键号"等约束。

## 三、四种用法

| 场景 | 给 AI 什么 | 关键点 |
|---|---|---|
| **A 写一份新蓝图** ★最常用 | `methodology\` + 你这个任务自己的背景材料 | 规范给正面结构，经验库给负面清单，两者合起来就够 |
| **B 执行一份已有的蓝图** | 该任务的总蓝图 + 该阶段的蓝图（**就两个**） | **不要给规范和经验库全文**——执行者读得越少越不容易被带偏 |
| **C 迁移到自己的项目** | `methodology\` | 用规范 §1–§10 全部 + 通用经验库（H/M）全部 + 具体坑库**只取形状**；具体条目多为 Node/Electron 场景，**参考形状、别照抄结论** |
| **D 查证某条经验** | `methodology\BLUEPRINT-经验库-全量台账.md` | 42k token，**用关键词定位，别整份读** |

**场景 A 的完整话术**：

```
你现在的任务是【写蓝图】，不是执行。

输入：
1. methodology\BLUEPRINT-撰写规范.md —— 写作规范，你的蓝图必须满足它的 §4（12 节结构）
2. methodology\BLUEPRINT-经验库-通用.md —— H/M 级经验，写之前先过一遍 §0 场景索引
3. methodology\BLUEPRINT-经验库-具体坑.md —— 只查我这个技术栈的那一章，别通读
4. <你这个任务的总蓝图>
5. <当前阶段文档 / 上一份完成报告>（至少读它的「五、关键偏差」与「十、回写清单」）

请产出「阶段 N 施工蓝图」，要求：
- 严格按撰写规范 §4 的 12 节结构
- 「非目标」逐条给"为什么不做"
- 「实测证据」一节写：支撑决策的实测数字，以及**被推翻的原计划**
- 每条验收判据要能判定，并写明失败处置；区分「充分判据」与「启发式指标」
- 写完自检：经验库 §6 的四类通用形状，本蓝图有没有踩
```

**场景 B 的完整话术**：

```
你现在的任务是【执行阶段 N】，不是写文档。

输入：
1. <该任务的总蓝图> —— 全局约束与已拍板决策（不得重新论证）
2. <PHASE-N 蓝图> —— 本阶段的施工蓝图，自包含

要求：
- 先核对蓝图第 3 节的「前置条件」（含"上阶段回写清单无未勾选项"），不满足就停下报告
- 遇到真实代码与蓝图冲突时，**以真实代码为准**，并记录下来
- 出现第 3 节的「停止条件」时立即停止并报告，不要自行绕过
- 执行完毕产出「完成报告」，10 节结构：
  执行摘要 / 最终状态 / 执行过程 / 验收逐项结果 / 关键偏差与判定修正 /
  已知坑复现情况 / 回退方法 / 交接清单 / 目标达成核对 / **回写清单（未勾完不得提交）**
```

## 四、两个角色读的不是同一批文件（最容易搞混）

| 角色 | 读什么 | 产出 |
|---|---|---|
| **写蓝图的人 / agent** | 撰写规范 + 经验库-通用 + 该任务总蓝图 + 上阶段报告的「关键偏差」与「回写清单」 | 下一份 **阶段蓝图** |
| **执行蓝图的人 / agent** | 该任务总蓝图 + 该阶段蓝图（**只需这两个**；规范只查 §4/§5/§8/§10 相关节） | 执行结果 + **完成报告** |
| **写报告的人 / agent** | 同上 + `BLUEPRINT-回写规范与清单模板.md` | 完成报告 + **回写清单** |

- 执行者**不需要**规范和经验库全文。
- 写的人**必须读**当前阶段文档——很多坑是执行时才发现的，那份文档是唯一载体。

## 五、这套体系的三个机制（v2.2 新增，最重要）

### 5.1 方法论与任务分离

```
methodology\      跨任务复用 —— 整体拷到另一个任务旁边，无需改动即可用
task-<任务名>\    任务专属 —— 总蓝图 / 阶段蓝图 / 报告 / 决策 / 人工台账
```

**为什么**：混在一起时，新任务的 agent 会读到**上一个任务的基线数值与已拍板决策**，
把别人的结论当自己的约束——这是"经验越用越错"的主要来源。
**跨目录引用一律用相对路径**（`../methodology/…`），不许写裸文件名。

### 5.2 经验分级（H / M / L）

| 等级 | 判据（自评问句） | 放哪 | 读法 |
|---|---|---|---|
| **H** | 换一种语言还成立吗？→ 是 | `经验库-通用.md` | 写蓝图前**必读** |
| **M** | 换同类框架还成立吗？→ 是（否 → L） | `经验库-通用.md` | 写蓝图前**必读** |
| **L** | 核心是命令 / API 行为吗？→ 是 | `经验库-具体坑.md` | **按当前技术栈检索，不通读** |

**避免的错**：把具体结论当通用知识套用。L 级条目只在那套技术栈成立，换栈要重新验证。

### 5.3 修正回写（**修正不能只活在报告里**）

| 触发 | 回写目标 |
|---|---|
| **T1** 判据被修正 | 判据台账（总蓝图 §9.1 / 规范 §7.2） |
| **T2** 基线数值被改写 | 总蓝图「当前基线」；**旧值移入「历史基线（仅存档）」** |
| **T3** 蓝图描述被实测推翻 | 总蓝图对应节；保留「**曾错、已修正**」说明 |
| **T4** 新增一条经验 | 经验库，**按 H/M/L 归位** |

- 完成报告末尾必须有「**回写清单**」四列表：触发条件 / 回写目标 / 回写内容 / 已勾选，
  **未勾选完不得提交**。
- 下一阶段前置条件含一条：**上阶段回写清单无未勾选项**（可 `grep` 验证）。
- **回写只「新增 + 标注」，不静默删除。**

## 六、出处引用怎么读（分享场景必读）

经验条目末尾的 `出处` 有两种形态：

```
① ../methodology/… 或同级文件名          ← 包内相对路径，直接可解析
② ../../2-证据.zip → SELF-update 260925/phase3-p3-erasure-and-console.md:1622-1646
                                          ← 解压 2-证据.zip 后按后面的子路径取
```

1. **引用是仓库相对路径，不是任何人的机器路径**——换电脑、换目录都不影响。
2. **不解析也没关系**。经验的价值**写在条目里**（错误做法 / 症状 / 根因 / 正确做法 四段完整），
   出处只承担两个作用：**溯源**（想看原始上下文时定位）与**唯一标识**（键号 C7 / D13 / R140 可直接引用）。
3. **要核对原始证据时**，解开 `2-证据.zip`，把引用路径的 `docs\` 换成解压后的对应目录：

   | 引用里写的 | 在 `2-证据.zip` 内的位置 |
   |---|---|
   | `docs/construction/SELF-update 260925/<文件>.md` | `SELF-update 260925\<文件>.md` |
   | `docs/merge-plan/<文件>.md` | `merge-plan\<文件>.md`（= `task-仓库合并\<文件>.md`） |
   | `docs/internal-issue/<文件>.md` | `internal-issue\<文件>.md` |
   | `docs/group-corpus.md` | `group-corpus.md` |

4. ⚠️ `2-证据.zip` 里的文档正文含**原作者的机器绝对路径**（`E:\AI_Chating\…`、`D:\data\node24`）。
   那是历史记录的原文，描述当时那台机器的环境——**当举例看，不要照抄执行**。
   `methodology\` 与 `给人读的使用说明\` 里**不含**任何机器绝对路径，可直接转发。

## 七、常见误用

| 误用 | 后果 | 正确做法 |
|---|---|---|
| 把 `2-证据.zip` 解开后一起喂给 AI | 多出约 28 万 token 的历史存档，淹没重点 | **保持 zip 形态**，只给 `methodology\` |
| 让 AI 通读 `methodology\` 全部 7 份 | 约 9 万 token | 按 `_先读这份-READ-FIRST.md` 的**最小必读集**读 2–3 份 |
| 把规范喂给**执行**者 | 执行者去纠结文档结构而不干活 | 只给总蓝图 + 阶段蓝图 |
| 写蓝图时不给上一份完成报告 | 重复踩已经踩过的坑 | 至少给上阶段报告的「关键偏差」+「回写清单」 |
| 只把文件夹丢过去、一句话不说 | AI 可能把"规范"当成"要执行的任务" | 用第二节 / 第三节的话术 |
| 拿 L 级经验的具体结论套别的技术栈 | 误伤无关代码 | 用**形状**自检，别照抄结论；L 级只在同栈复用 |
| 把 `task-仓库合并\` 的总蓝图当模板 | 别人的基线与决策变成你的约束 | 换任务时重写总蓝图，`methodology\` 才复用 |
| 修正只写进完成报告 | 后续阶段得翻遍旧报告才知道按哪版执行 | 按 T1–T4 **回写**，清单未勾完不提交 |

## 八、这是快照：怎么判断是否过期

**本包是某一时刻的快照，上游仍在演进。** 实测：本包生成前后 20 分钟内，
规范就从 v2.0 走到了 v2.1（蓝图 11 节 → 12 节、新增「人工环节」），某阶段文档从 501 行重写到 1054 行。

| 检查点 | 本快照的值 |
|---|---|
| 规范版本号（文件抬头 `> **版本**`） | **v2.2** |
| 施工蓝图必备结构 | **12 节**（含「五、人工环节」） |
| 完成报告必备结构 | **10 节**（含「十、回写清单」） |
| 经验库分级 | **H / M / L 三级**，拆为「通用」（H+M）+「具体坑」（L）+「全量台账」 |
| 目录结构 | `methodology\` + `task-仓库合并\` **双目录分离** |
| 通用库条数 | **56**（H 44 + M 12） |
| 具体坑库条数 | **54**（原取样 43 + 附录 B 的 X 系列 11 条 + 1 条改判） |
| 全量台账条数 | **186 条**（R1–R186）+ 附录 B 的 10 条 X（每条带 `- 等级:`） |
| `methodology\` 文件数 | **8 份**（规范 / 回写规范 / 3 个经验库 / 2 个模板 / READ-FIRST） |

任何一项对不上，说明上游已经往前走了，请向分发者索取新版本。

**如果你在维护它**：本包是**分发产物**而不是**编辑对象**。
在上游仓库里改，然后重新生成整个包（保持同样的目录结构与路径映射）。
**不要**只手改包内某一份，那会让包内版本互相不一致。
