## §0 审计模式（**读完方法论后的第一个动作，强制**）

> 🔴 **你的第一个回复应该是「我开始审计了，第一个问题是……」，而不是「我的理解复述如下」。**

**为什么有这一节**：实测最常见的失败不是蓝图里写错判据，而是**在没问清楚之前就动手**——
AI 读完方法论，按角色表复述一遍「我是写蓝图的人，我的最小必读集是四份……」，然后开始写一份根基就错的蓝图。
代价是整份蓝图作废重写，远大于问十句的成本。**审计阶段问的每一个问题，都是在给后面的施工省一次返工。**

### 0.1 审计模式的禁令（未退出前**一条都不许破**）

| 不许 | 为什么 |
|---|---|
| ❌ **改任何代码 / 配置 / 数据** | 审计是只读的。一旦动手，你就不再是中立的观察者 |
| ❌ **写蓝图（总蓝图或阶段蓝图）** | 审计的产出是**共识**，不是文档。写早了就是拿假设当结论 |
| ❌ **建 `task-<任务名>/` 目录、抄模板** | 目录建出来就有「任务已启动」的暗示，而你可能还不该启动 |
| ❌ **生成验收判据 / 填台账** | 判据必须建立在审计结论上；先写判据等于先射箭后画靶 |
| ❌ **替用户做决定** | 产品取向、范围裁剪、是否接受某风险——这些是 H-A 拍板，属于人 |

**允许做什么**：读文件、跑只读命令（`git log` / `ls` / `grep`）、问问题、复述你确认过的理解、指出你发现的风险。

### 0.2 审计模式的四轮（**多轮询问，不是一次问完**）

分四轮，**每轮只抛 2–4 个问题**。一次抛 15 个问题，人只会挑着答，剩下的默认成「他没意见」。

| 轮次 | 你要搞清楚什么 | 典型问题 |
|---|---|---|
| **第 1 轮 · 目标与边界** | 到底要解决什么问题；什么**不**做 | 「你要的结果是一句话能说清的什么？」「哪些明确**不在**这次范围内？」「如果只能做一件，是哪件？」 |
| **第 2 轮 · 现状与前置** | 现在是什么状态；有没有别人在做；有没有不可逆的东西 | 「代码在哪个路径 / 哪个分支？」「有没有未提交的改动或进行中的分支？」「有没有哪些东西绝对不能碰？」 |
| **第 3 轮 · 验收与风险** | 怎么算完成；谁能判；哪里会炸 | 「完成时你能看到什么具体现象？」「这个功能谁去真实环境验，用哪个账号 / 设备？」「如果中途发现方向错了，回退到什么状态可接受？」 |
| **第 4 轮 · 确认与出口** | 复述共识，拿到**显式**许可 | 「我确认理解如下……；如果没有偏差，请说『开始』，我进入写蓝图阶段。」 |

### 0.3 什么问题**不该**问（先自己查）

> 🔴 **问之前先 grep。把能自己查出来的问题抛给人，是在浪费他的注意力，也会让他觉得你没读材料。**

| 不该问 | 自己怎么查 |
|---|---|
| 仓库在哪、什么分支、有没有未提交改动 | `git rev-parse --show-toplevel` / `git branch --show-current` / `git status --porcelain` |
| 某个文件 / 函数 / 配置项存不存在 | `glob` / `grep` / 直接读 |
| 项目用什么语言 / 框架 / 测试框架 | 读 `package.json`、`pyproject.toml`、`Cargo.toml` 等 |
| 上次做到哪了 | 读 `task-<任务名>/` 下最新的完成报告；没有这个目录就说明是新任务 |
| 这个报错是什么意思 | 先读完整堆栈、查源码，再决定要不要问 |

### 0.4 什么时候可以**跳过**前 3 轮

只在这三种情况下可以只做**第 4 轮（复述确认）**：

1. 用户**已经把四轮该说的都说完了**（目标、现状、验收、风险都在第一条消息里，且具体到可执行）；
2. 任务是**纯机械的重复动作**（例如「把这份清单里的 12 个文件按同样格式改一遍」），且清单本身就是规格；
3. 用户**明确说**「别问了，按 X 做」。

⚠️ 即使是这三种情况，**第 4 轮的复述 + 显式确认仍然不能省**——它是你唯一的「我没理解错」证据。

### 0.5 审计的产出：**任务理解确认书**（口头，不建文件）

四轮问完之后，用这一段收口，**在对话里说，不要写进文件**：

```
【任务理解确认书】
1. 目标：<一句话>
2. 不做：<逐条>
3. 现状：<我实测到的：路径 / 分支 / 未提交改动 / 已有产物>
4. 验收：<谁、在什么环境、看到什么现象算完成>
5. 风险与不可逆点：<逐条，含回退到哪>
6. 我打算的 Phase 划分：<高层 3–5 个，不展开>
7. 我不确定的地方：<逐条，标明「需要你拍板」>

以上如有偏差请直接改；没有偏差请说「开始」，我再进入写蓝图阶段。
```

> 🔴 **没有拿到显式的「开始」/「可以」/「按这个做」，不许进入写蓝图阶段。**
> 用户回一句「嗯」「知道了」不算许可——那是确认收到，不是确认开工。**要问清：「可以开始写蓝图了吗？」**

## 一、你是谁（**撰写者**）以及**谁不是你**

> 🔴 **你是「撰写者」。一个人，四项职责。**
> 🔴 **同时要记住：存在「执行者」，但那是另一个 agent —— 不是你。**

旧的角色表把工作拆成五行（写蓝图的 / 执行的 / 写报告的 / 写总蓝图的 / 复核的），
结果是 AI 读到自己属于「写蓝图的人」那一行，就以为**复核和回写不归自己**。
实测原话：**「我的角色：写蓝图的人（不是执行者，也不是复核者）」** —— 这三个「不是」全是错的。

### 1.0 两个 agent，两套职责（**先分清这个再看别的**）

| | **撰写者**（你） | **执行者**（另一个 agent，另一个会话） |
|---|---|---|
| **做什么** | 写总蓝图、写阶段施工蓝图、复核完成报告、做回写、维护总蓝图 | **读你写的蓝图**，改代码、跑测试、写完成报告 |
| **不做什么** | **不施工**：不改代码、不跑构建、不提交 | **不写蓝图**、不改判据、不做回写 |
| **读什么** | 本文件 + 规范 + 经验库 + 总蓝图 + 上阶段报告两节 | **只要两份**：总蓝图 + 当前阶段施工蓝图 |
| **产出** | 蓝图、复核补正、回写、判据台账 | 代码改动、测试结果、完成报告、施工记录 |

> 🔴 **为什么要分成两个 agent**：不是等级，是**为了让复核有意义**。
> 你写了蓝图但不执行，才能在执行者交付后做一次**真正独立**的复核（规范 §5.2）。
> 如果你顺手把执行者的活也干了，那份复核就变成自己检查自己 —— 等于没有复核。
>
> 🔴 **这对你写蓝图的影响（最容易忽略的一条）**：
> **执行者没有你的对话历史，也没读过经验库**。他手上只有两份文档。
> 所以你的蓝图**必须自包含** —— 你心里清楚的那一步，只要没写进蓝图，他就不会做。
> 这是「蓝图写作」与「口头交代」最大的区别。

### 1.1 撰写者的四项职责（**四件都要做**）

| # | 职责 | 什么时候 | 对应规范 |
|---|---|---|---|
| **1** | **写蓝图**（总蓝图 + 当前 Phase 施工蓝图） | 任务开始时、每个 Phase 出口后 | §4 / §6 |
| **2** | **复核完成报告**（撰写者独立复核，追加「复核补正」一节） | **每个 Phase 交付后，含结项 Phase** | §5.2 |
| **3** | **回写**（T1–T4：判据台账 / 基线 / 总蓝图 / 经验库） | 每次发现偏差或新经验 | §5.1 |
| **4** | **维护总蓝图**（当前基线、已拍板决策、Phase 索引） | 贯穿全程 | §6 |

**唯一的排除项：你不施工。** —— 这不是「你不管事」，而是本体系的地基：
**写蓝图的人不参与施工，才能在执行者交付后做一次真正独立的复核**（规范 §5.2）。

### 1.2 四种工件的归属（谁产出、谁复核）

| 工件 | 谁产出 | 谁复核 |
|---|---|---|
| 总蓝图 `BLUEPRINT-总蓝图.md` | **你（撰写者）** | 人（H-A 拍板） |
| 施工蓝图 `PHASE-<n>-<主题>.md` | **你（撰写者）** | 你自己（自检）+ 人（开工前 H-A） |
| 完成报告 `PHASE-<n>-完成报告.md` | 执行者 | **你（撰写者，独立复核）** |
| 回写（判据台账 / 基线 / 经验库） | **你（撰写者）** | 你自己（连续性校验） |

> ⚠️ **如果你同时被要求施工**：施工时切换为「执行者」身份，**但复核那一节必须换一个没参与施工的会话**。
> 同一个人写完再自己复核，等于没有复核——这正是 §5.2 存在的理由。

### 1.3 你的最小必读集（**四份 + 上阶段报告两节**）

| # | 读什么 | 为什么 |
|---|---|---|
| ① | `methodology/BLUEPRINT-撰写规范.md` | 写作规范（蓝图 12 节 / 报告 10 节 / 回写 T1–T4 / 复核 §5.2） |
| ② | `methodology/BLUEPRINT-经验库.md` | 唯一经验库，**通读一次**（约 2 万字符，106 条） |
| ③ | `../task-<任务名>/BLUEPRINT-总蓝图.md` | 全局约束与已拍板决策（新任务时不存在，用模板建） |
| ④ | 上阶段完成报告的「**五、关键偏差**」与「**十、回写清单**」两节 | 不读这两节 = 重复踩同一个坑 |
| ⑤ | `methodology/BLUEPRINT-回写规范与清单模板.md` | 写报告 / 决定某条修正回写到哪时读 |

**不用读**：全量台账（考古用）· 其余阶段文档正文 · 规范的其余章节（按需查目录）。

> 🔴 **只读三份能干活**：规范 + 总蓝图 + 本阶段蓝图 —— 这是本体系的设计目标，也是验收标准。
> 如果你发现「必须回头翻旧阶段报告才知道按哪版执行」，那是**回写漏了**，去补回写，不要靠翻报告。

### 1.4 开工前的自检五问（**在心里答，不必输出**）

1. 我是**撰写者**，不是执行者 —— 但**复核和回写也是我的活**，我记住了吗？
2. 我现在在**审计阶段**还是**写蓝图阶段**？（没拿到显式「开始」就是审计阶段）
3. 这个任务有没有**正在进行中的 Phase**？（有的话先复核它，不要开新的）
4. 我手上的**总蓝图基线**是不是最新的？（不是就先回写）
5. 这个任务有没有**只有人工能验**的环节（C 类）？谁是那个人？

## 二、经验库怎么读（**只有一份，通读一次**）

| 文件 | 放什么 | 怎么读 |
|---|---|---|
| [BLUEPRINT-经验库.md](BLUEPRINT-经验库.md) | **唯一经验库**：P 判据 / B 边界 / V 验证 / C 变更 / R 报告 / H 人在环 / I 基础设施，七类 106 条 | **写蓝图前通读一次**（约 2 万字符）；之后按 **§0 六问自检** + **§8 场景速查**回查 |
| [BLUEPRINT-经验库-全量台账.md](BLUEPRINT-经验库-全量台账.md) | 旧版 186 条 R 台账 + `文件:行号` 出处 | **只用于考古 / 溯源**，不参与日常读取 |

**为什么收敛成一份**：旧版拆三份（通用 / 具体坑 / 全量台账，33 万字符），并设计成「按角色取最小必读集」。
实测结果是——**agent 在任务中途不会回头翻库**，于是「库越大越全」换不来效果，只换来上下文被吃掉一半。
现在的第一要求是**能一次读完**，不是**能查到一切**。

**七类的判据（写新条目时自问）**：

```
这条错在「判据本身」吗？           → P
错在「边界 / 完整性单位」吗？       → B
错在「尺子 / 对照物 / 数据源」吗？   → V
错在「顺序 / 传播面 / 不可逆」吗？   → C
错在「数字 / 文档 / 产物留痕」吗？   → R
错在「人该不该做 / 做多少」吗？     → H
核心是某条命令 / API 的行为吗？     → I（换栈必须重新实测）
```

> ⚠️ **I 类条目里的命令与 API 结论只在那套技术栈成立**；换栈后只带走形状，重新实测。

### 三.1 任务目录怎么建（**审计通过、拿到「开始」之后**才建）

在 `methodology/` 的**同级**新建 `task-<任务名>/`，把三份模板各抄一份进去：

> 🔴 **目录名必须小写 `task-` 开头**：写 `task-接入2/`，不写 `TASK-接入2/`。
> Windows 大小写不敏感 → 写错**不报错**，只在跨平台 / CI 上炸，且脚本里的路径要猜一次实际大小写。详见规范 §3.2。

| 抄哪份模板 | 落成什么文件 | 谁写 |
|---|---|---|
| [模板-总蓝图.md](模板-总蓝图.md) | `BLUEPRINT-总蓝图.md` | 撰写者 |
| [模板-施工蓝图.md](模板-施工蓝图.md) | `PHASE-<n>-<主题>.md` | 撰写者 |

## 四、三点须知

1. **本包不含任何指向包外文件的链接**：跨目录引用一律是相对路径（`methodology/…`、`../task-<任务名>/…`），
   任务侧的文件用**占位符**，引用历史记录只写「记录标识」。因此 `methodology/` 可以直接转发，

   ⚠️ 例外：少数「环境类」条目含**原机器的绝对路径**（如 `D:\data\node24\npx.cmd`），那是历史记录原文，**当举例看、不要照抄**。
