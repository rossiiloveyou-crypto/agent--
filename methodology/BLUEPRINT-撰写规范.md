# 蓝图撰写规范

> **文档定位**：本文件是**写作规范**，位于 `methodology/`（**方法论目录，跨任务复用**）。
> 读者是**撰写者**。撰写者**不碰工程文件**：不施工、不改代码、不跑构建、不提交。产出是**文档与判断**。
>
> 🔴 **必须知道：存在「执行者」，但那是另一个 agent，不是你。**
> - **撰写者**（你）：写总蓝图、写阶段施工蓝图、复核完成报告、做回写。**不施工。**
> - **执行者**（另一个 agent，另一个会话）：**读你写的蓝图**，按它改代码、跑测试、写完成报告。
>
> 这个分工不是为了「谁地位高」，而是**为了让复核有意义**：你写了蓝图但不执行，才能在执行者交付后做一次真正独立的复核（§5.2）。
> 如果你顺手把执行者的活也干了，那份复核就变成自己检查自己 —— 等于没有复核。
>
> **执行者读什么**：只要 `BLUEPRINT-总蓝图.md` + 当前 `PHASE-<n>-<主题>.md` 两份，**不读本规范全文、不读经验库**（§3.3）。
> 这意味着：**你的蓝图必须自包含** —— 执行者没有你的对话历史，也没有你读过的经验库；写漏一步，他就漏做一步。
>
> **自包含声明**：本文件 + 当前任务的「总蓝图」+ 当前 Phase 文档，应当足以让一个**没有对话历史**的 agent 写出合格的下一份蓝图。
> **经验库只有一份**：[BLUEPRINT-经验库.md](BLUEPRINT-经验库.md)（约 2 万字符，106 条，**写蓝图前通读一次**），本规范正文只做引用，不复述。
> 若新会话里**只拿到本文件、拿不到经验库**：§9 的追加义务跳过即可，其余各节仍然成立。
>
> **读取纪律**：**不要通读 `methodology/`**。读 §3.3 的最小必读集即可开始干活；
> 经验库通读一次，之后按 §0 六问自检 + §8 场景速查回查。
>

## §1 六条第一原则

### 原则 0 · 先审计，再动手（**最高优先级**）

> 🔴 **读完方法论后的第一个动作不是写蓝图，是审计。**

**为什么把它放在原则 1 前面**：本规范其余十条都在讲「蓝图怎么写好」，但它们全部以「我已经知道要写什么」为前提。
实测最贵的失败不在蓝图层，而在**动手太早**——写出来的蓝图根基是错的，整份作废。
审计的成本是几轮对话，不审计的成本是一份蓝图 + 一次施工。

#### 0.1 审计模式的禁令

| 不许 | 为什么 |
|---|---|
| ❌ 改任何代码 / 配置 / 数据 | 审计是只读的。一旦动手，你就不再是中立的观察者 |
| ❌ 写蓝图（总蓝图或阶段蓝图） | 审计的产出是**共识**，不是文档。写早了就是拿假设当结论 |
| ❌ 建 `task-<任务名>/` 目录、抄模板 | 目录建出来就有「任务已启动」的暗示，而你可能还不该启动 |
| ❌ 生成验收判据 / 填台账 | 判据必须建立在审计结论上；先写判据等于先射箭后画靶 |
| ❌ 替用户做决定 | 产品取向、范围裁剪、是否接受某风险 —— 这些是 H-A 拍板，属于人 |

**允许**：读文件、跑只读命令、问问题、复述你确认过的理解、指出你发现的风险。

#### 0.2 四轮询问（**每轮 2–4 个问题，不要一次抛完**）

| 轮次 | 搞清楚什么 | 典型问题 |
|---|---|---|
| **1 目标与边界** | 要解决什么；什么**不**做 | 你要的结果一句话是什么？哪些明确不在范围内？只能做一件的话是哪件？ |
| **2 现状与前置** | 现在什么状态；有没有别人在做；哪里不可逆 | 代码在哪个路径 / 分支？有没有未提交改动？哪些东西绝对不能碰？ |
| **3 验收与风险** | 怎么算完成；谁能判；哪里会炸 | 完成时你能看到什么现象？谁去真实环境验、用哪个账号？方向错了回退到什么状态可接受？ |
| **4 确认与出口** | 复述共识，拿**显式**许可 | 我确认理解如下……没有偏差请说「开始」。 |

#### 0.3 先自己查，再问人

> 🔴 把能自己查出来的问题抛给人，是在浪费他的注意力，也会让他觉得你没读材料。

| 不该问 | 自己怎么查 |
|---|---|
| 仓库路径 / 分支 / 未提交改动 | `git rev-parse --show-toplevel` / `git branch --show-current` / `git status --porcelain` |
| 某文件 / 函数 / 配置项在不在 | `glob` / `grep` / 直接读 |
| 用什么语言 / 框架 / 测试框架 | 读 `package.json` / `pyproject.toml` / `Cargo.toml` |
| 上次做到哪了 | 读 `task-<任务名>/` 下最新的完成报告；没有目录 = 新任务 |

#### 0.4 审计的出口：任务理解确认书（口头，不建文件）

```
【任务理解确认书】
1. 目标：<一句话>
2. 不做：<逐条>
3. 现状：<我实测到的：路径 / 分支 / 未提交改动 / 已有产物>
4. 验收：<谁、在什么环境、看到什么现象算完成>
5. 风险与不可逆点：<逐条，含回退到哪>
6. 我打算的 Phase 划分：<高层 3–5 个，不展开>
7. 我不确定的：<逐条，标明「需要你拍板」>

以上如有偏差请直接改；没有偏差请说「开始」，我再进入写蓝图阶段。
```

> 🔴 没有拿到显式的「开始 / 可以 / 按这个做」，不许进入写蓝图阶段。
> 用户回一句「嗯」「知道了」不算许可 —— 那是确认收到，不是确认开工。要问清：「可以开始写蓝图了吗？」
>
> **可以不问直接进第 4 轮的三种情况**：① 用户第一条消息里四轮该说的都说了且具体到可执行；② 任务是纯机械重复动作且清单本身就是规格；③ 用户明确说「别问了，按 X 做」。
> 即使这三种，**第 4 轮的复述 + 显式确认仍然不能省** —— 它是你唯一的「我没理解错」证据。

### 原则 1 · 为 agent 的可读性而写，不为人的美观而写

蓝图是**给 agent 读的执行手册**。判据：

- 每条改动能落到 `文件:行号`，或落到一条**可粘贴执行**的命令
- 禁止「优化一下相关逻辑」「按需处理」这类无法执行的表述
- 表格优先于散文；命令优先于描述；数字优先于形容词

### 原则 2 · 每步必须可判定，且失败必须能停

**任何一步都要附一条可执行命令**，并且：

| 要求 | 说明 |
|---|---|
| 输出可判定 | 数字比对 / 退出码 / 字符串存在性 |
| 有期望值 | 写清「期望 = 多少」，不是「应该没问题」 |
| 有容差 | 会随时间涨的量（审计行数、语料字节）必须写明容差或改成相对判据 |
| 有停止条件 | 不满足时**立即停止并报告**，不得带着失败进入下一 Phase |
| 有失败处置 | 不是 26 时该查什么、该回退到什么状态 |

### 原则 3 · 承认蓝图可能错，并把纠错机制写进蓝图

你无法预知蓝图是否绝对正确。因此在**总蓝图与每个 Phase**里都必须写明：

> 执行者应根据实际情况判断方案正误；发现错误时**明确指出、写入完成报告**；
> 遇到真实代码与蓝图冲突时，**以真实代码为准**。

这条不是客套——实战中它抓出的最大一类缺陷（例：控制台删除漏删向量、她的复述行不在擦除范围）
都是**蓝图本身没预见到**的，靠执行者的现场判断才发现。

### 原则 4 · Phase 串行施工，不得提前生成后续阶段蓝图

本体系采用**严格的 Phase 串行推进模型**。

> 🔴 **当前 Phase 未完成 → 绝对禁止生成下一 Phase 的施工蓝图。**

具体要求：

- **任意时刻只能存在一个处于「施工中」状态的 Phase**。
- Agent 每次只允许撰写、执行当前 Phase 的施工蓝图。
- 不得在当前 Phase 尚未完成前，提前生成：
  - 下一 Phase 的施工蓝图；
  - 后续多个 Phase 的连续施工蓝图；
  - 以“方便后续执行”为理由提前冻结后续施工步骤。
- **允许在总蓝图中保留后续 Phase 的高层目标、依赖关系和 Phase 索引，但不得提前生成后续 Phase 的具体施工蓝图。**

当前 Phase 必须依次完成以下闭环：

```
当前 Phase 施工蓝图
      ↓
   执行施工
      ↓
功能 / 阶段验收
      ↓
   完成报告
      ↓
  回写 T1–T4
      ↓
 撰写者独立复核
      ↓
  出口条件满足
      ↓
【允许生成下一 Phase 蓝图】
```

#### 1.1 下一 Phase 的生成门禁

只有同时满足以下七项条件，才允许生成 `PHASE-<n+1>-<主题>.md`：

| 门禁代号 | 门禁要求 | 验证依据 |
|---|---|---|
| **G1** | 当前 Phase 已提交完成报告 | 存在 `task-<任务名>/PHASE-<n>-完成报告.md` |
| **G2** | 完成报告状态为 ✅ 已完成，或明确满足允许进入下一 Phase 的部分完成出口条件 | 报告抬头 `> **状态**` |
| **G3** | §十「回写清单」所有触发项均已闭合 | 报告末尾四列表无未勾选 `[ ]`（见 §5.1） |
| **G4** | 当前 Phase 的撰写者复核已经完成 | 报告包含 §十三 撰写者复核补正且结论明确允许出口（见 §5.2） |
| **G5** | `HUMAN-人工验证台账.md` 中不存在阻塞当前 Phase 出口的未闭合 H-A / H-B / H-F | 台账中无未闭合阻塞项、无未知终态（见 §4.1.3） |
| **G6** | 当前 Phase 的交接清单已经形成 | 完成报告 §八 给下一个 Phase 的交接清单条目清晰可用 |
| **G7** | 总蓝图已经完成必要回写，当前基线与判据口径已经同步 | 总蓝图最新基线已覆盖本 Phase 变动（见 §6） |

> 🔴 **任意一项不满足 → 禁止生成下一 Phase 施工蓝图。**

#### 1.2 「总蓝图提前规划」与「阶段蓝图提前生成」必须区分

| 允许（全局路线规划） | 禁止（阶段蓝图提前生成） |
|---|---|
| **总蓝图**提前规划全局路线：<br>• P1 侦察<br>• P2 数据处理<br>• P3 QQ 接入<br>• P4 多渠道适配 | **阶段施工蓝图同时存在并等待执行**：<br>❌ P1 施工蓝图<br>❌ P2 施工蓝图<br>❌ P3 施工蓝图<br>❌ P4 施工蓝图 |

**总蓝图负责描述全局路线；Phase 蓝图负责描述当前阶段如何实际施工。**
只有前序阶段踩完坑、拿到实测证据并完成复核，后续阶段的施工细节才具备确定性。提前生成只会导致大面积失效重写。

### 原则 5 · 「代码完成」不等于「功能完成」，功能级必须人工验收

任何 Phase 中，**只要新增、修改或恢复了一个可独立使用的功能，该功能必须经过与真实使用场景相匹配的人工验证后，才能标记为「完成」。**

> 🔴 **Agent 自测通过 ≠ 功能完成。**

Agent 可以完成：编译、单元测试、集成测试、自动化测试、API 测试、日志检查、数据检查、静态分析；
**但上述结果不能替代需要真实人类操作才能证明的功能验收。**

#### 2.1 功能级人工验收门禁

**先分档，再走闭环**（分档口径见 §4.1.0）：
- **O 档（选验）**：机器判据给出同等强度的结论即可关闭，**不阻塞出口**；报告写明「由 A 类判据关闭」。
- **M 档（必验）**：必须走完下面这条闭环，缺一环都不算完成。

M 档功能的验收闭环：

```
    功能实现
       ↓
 Agent 自动测试
       ↓
  自动测试通过
       ↓
 登记人工验证 H-nn
       ↓
   人类真实操作
       ↓
  真实环境验证
       ↓
人工验证台账原地回写
       ↓
功能才允许标记为「完成」
```

- **如果人工验证失败**：`功能状态 ≠ 完成` → 修复 → 重新人工验证。
- **如果人工验证因为环境原因暂时无法进行**：`功能状态 ≠ 已完成` → 记录 `🚫 无法验` / `⏳ 待人眼` → 进入 `BACKLOG-长期待办.md` → 满足条件后重新验证。

> 🔴 **严禁借口（仅针对 M 档）**：不得因为“代码已经写完”、“测试已经通过”、“本地运行正常”、“理论上应该可以”、“API 返回正常”、“Agent 自己测试过了”而跳过**M 档**的人工验收。
> 反过来，**也不许把机器判得了的事硬塞给人**——O 档该机器关就机器关，否则台账会变成人肉复算脚本的场所，最后没人看。

#### 2.2 C 类功能必须进行真实环境验证

涉及真实外部渠道、真实第三方服务、真实设备、真实账号或真实用户交互的功能，原则上属于 **C 类人工验证**。

典型场景包括但不限于：
- QQ、微信、Telegram、Discord 等真实即时通讯渠道；
- 手机端、移动设备；
- 浏览器真实页面交互；
- 第三方 OAuth 授权登录；
- 外部实际生产/测试 API；
- 真实消息通道与推送；
- 真实文件上传 / 下载；
- 真实系统通知；
- 真实支付或订单环境；
- 真实外设或硬件通信。

**此类功能必须在真实目标环境中验证。**

##### 真实验证示例：AI 接入 QQ 对话功能

若某 Phase 新增：AI 接入 QQ，能够读取 QQ 消息、调用 AI 模型、并将 AI 回复发送回 QQ。
**绝对不能仅以**：`API 测试通过 ↓ 模拟 QQ 消息通过 ↓ 日志显示 sendMessage 成功` 判定完成！
必须由人类在真实 QQ 客户端中进行验证，标准步骤如下：

1. **人工使用真实 QQ 登录 / 接入系统**；
2. **从真实 QQ 客户端向系统发送测试消息**；
3. **确认系统真实收到 QQ 消息**；
4. **确认消息正确进入 AI 处理链**；
5. **确认 AI 生成回复**；
6. **确认系统真实将回复发送回 QQ**；
7. **人工在 QQ 客户端确认回复实际出现**；
8. **如功能包含上下文 / 多轮对话，再进行至少一轮连续真实对话**。

最终必须在 `task-<任务名>/HUMAN-人工验证台账.md` 对应的 `H-nn` 行中如实记录：
要验什么、期望值、人工实际结果、验证日期、真实环境、原始证据（截图哈希、日志片段等）。

#### 2.3 功能级验收与 Phase 级 H-B 是两层门禁（**只约束 M 档**）

新增的功能级人工验收（H-F）不是对原 H-B 的替代，两者职责截然不同：

| 层级 | 验收对象 | 作用与时机 |
|---|---|---|
| **功能级人工验收（H-F）** | **单个独立功能** | 每个功能完成后立即进行，判断**这个具体功能是否真的可用** |
| **Phase 完工评审（H-B）** | **整个 Phase** | Phase 全部功能施工与自测完毕后进行，判断**本阶段整体是否可以退出** |
| **人工验证台账** | **全量验证记录** | 保存所有 H-nn 的**唯一真实状态**，跨 Phase 累积 |

因此标准推进顺序为：

```
功能 A ──→ 人工验收 (H-01) ──→ 通过
功能 B ──→ 人工验收 (H-02) ──→ 通过
功能 C ──→ 人工验收 (H-03) ──→ 通过
                  ↓
          全部达到 Phase 要求
                  ↓
         H-B Phase 完工评审
                  ↓
              完成报告
                  ↓
              下一 Phase
```

> 🔴 **不得用一次 Phase 末尾的 H-B，替代中间每个 M 档功能应有的即时人工验证。**
> O 档功能不需要在中间即时验，跟 H-B 一起扫一眼或直接由机器关闭都可以。

#### 2.4 功能完成状态必须可追踪

施工蓝图中的功能清单必须使用以下七种明确状态：

| 状态 | 含义 | 说明 |
|---|---|---|
| ⬜ **未开始** | 尚未施工 | 任务尚在待办状态 |
| 🔨 **施工中** | 正在实现 | Agent 正在修改代码或搭建配置 |
| 🤖 **自动测试通过** | Agent 自动测试已通过 | 机器判据已绿，但**尚未完成人工验收，不得宣称完成** |
| 👁 **待人工验证** | 已具备人工验收条件 | 功能就绪，台账 H-nn 已预填完毕，等待人类操作 |
| 🚫 **无法人工验证** | 当前环境无法完成真实验证 | 外部依赖或环境受阻，必须登记并进入 BACKLOG |
| ❌ **人工验证失败** | 真实人工测试失败 | 功能存在缺陷，退回修复，不得标记完成 |
| ✅ **人工验证通过** | 人工真实验证通过 | **只有本状态才允许将需要人工验收的功能标记为「完成」** |

**硬规则**：
- **只有 ✅ 人工验证通过 才能将需要人工验收（M 档）的功能标记为「完成」。** O 档由机器判据关闭后即可标记完成。
- 对于纯机器可验证、明确不需要人工判断的内部逻辑功能，可以由 A 类机器判据直接闭合，但**必须在蓝图中明确说明**：`本功能不需要人工验收，理由：……`。不得默认所有功能都可以跳过人工验证。

## §2 全局约束（所有 Phase 共同遵守）

### 2.1 工具与工作区边界

| 规则 | 说明 |
|---|---|
| **只读优先** | 分析类工作（审计、比对、核查）不得写文件 |
| **不碰工作区内容** | 除明确要求改动的文件外，不得 `checkout` / `reset --hard` / `stash push` |
| **非 ASCII 文件名** | 文件名含中文时**禁止逐文件脚本复制**（会静默丢文件）；用 `git` 机制或 `robocopy` |
| **文件遍历** | 一律用 `git ls-files` / `git ls-tree` / `findstr`，不要 `Get-ChildItem` 递归拼路径 |
| **不可逆动作先备份** | 任何"销毁"类动作之前，先做**外部**备份并记下路径（应用内备份可能正是被销毁的对象） |

### 2.2 命令执行规范

```powershell
# 每条命令前显式设置编码（避免中文乱码）
[Console]::OutputEncoding = [System.Text.Encoding]::UTF8
$OutputEncoding = [System.Text.Encoding]::UTF8

# 本机是 PowerShell 5.1（无 pwsh）：不能用 &&，括号表达式里不能用 ; 连接命令
# 文件遍历一律用 git（不要 Get-ChildItem 递归拼路径）
git -c core.quotepath=false ls-files --others --exclude-standard

# 判定 robocopy 成功：看汇总的 FAILED 与 Mismatch 列，不看退出码（9 可能是假警报）
```

### 2.3 环境陷阱（详见经验库 §7 基础设施坑）

编码、`2>&1` 污染变量、非 ASCII 路径转义、`NUL` 幻影目录、Node 版本不随会话传播——
都属**已实测复现过**的坑。写进蓝图时必须**直接给出规避写法**，不要只写"注意"。
（经验库 §7 基础设施坑给具体写法；跨栈的形状见 §0 六问自检。）

### 2.4 提交粒度

- 每个 Phase 结束后**单独提交一次**（便于回退到任意 Phase 边界）
- 提交信息格式：`<域>(P<n>): <做了什么>`
- **禁止**把多个 Phase 混在一个提交里
- **若任务本身要求"不提交"**（例如合并冲突未解决完），必须在每个 Phase 明确写出"仍不要提交"
- 🔴 **WIP 阈值门禁**（**v2.4 新增**）：**待提交改动 > 20 条** 或 **最后一次提交距今 > 3 天** → **先提交（或开 `wip/` 分支）再继续**。
  可机械判定：`(git status --porcelain | Measure-Object).Count` 与 `git log -1 --format=%cr`；把它写进阶段蓝图的**前置条件**。
  **为什么**：一次真实事故里，攒了 **12 天**未提交的改动 → **46 个冲突**，而非冲突区还被三方合并按"谁改谁赢"混入双方内容、
  事后无法逐笔归因，也没有任何基线可回（经验库 **F23**）。未提交改动同时在**冲突面 / 归因能力 / 回滚能力**三个方向累积风险。

## §3 文档族与命名规范

### 3.1 三类文档的分工（缺一不可）

| 文档 | 谁写 | 谁读 | 职责 | 什么时候写 |
|---|---|---|---|---|
| **总蓝图** | **撰写者** | 撰写者 + **执行者** | 索引 + 全局约束 + 已拍板决策 + 当前基线 | 开工前，之后**持续同步** |
| **施工蓝图** | **撰写者** | **执行者**（另一个 agent） | 本 Phase 怎么改、怎么验、怎么退 | 执行者开工前 |
| **完成报告** | **执行者**（另一个 agent） | **撰写者（复核）** | 实际发生了什么、与蓝图差在哪、交接什么 | 执行后**立即** |

> 🔴 **撰写者写前两份、读第三份；执行者读前两份、写第三份。**
> 完成报告是**执行者**的产出，撰写者的职责是对它做**独立复核**（§5.2）。
> 复核的全部价值在于「没参与施工」—— 自己动手再自己复核，等于没有复核。

### 3.2 命名规范（实测口径）

| 类型 | 命名 | 放哪 | 示例 |
|---|---|---|---|
| 总蓝图 | `BLUEPRINT-总蓝图.md` | `task-<任务名>/` | 同左 |

> 写 **`task-sl接入2/`**，不写 `TASK-sl接入2/`、不写 `Task-sl接入2/`。
>
> **为什么专门规定这一条**：Windows 文件系统**大小写不敏感**，所以 `TASK-xxx` 和 `task-xxx` 在本机**行为完全一样、不报任何错** ——
> 只有到了大小写敏感的 **Linux / CI** 上才会找不到目录，而那时错误信息指向的是路径，不是命名规则；
> 同时 `grep` / 脚本里的每条路径都得先猜一次实际大小写。
> 实测病灶：本包的**占位目录曾经自己就叫 `TASK-NAME`**，于是真实任务的目录被照抄成 `TASK-SL接入2` ——
> **规范说 task-、示例写 TASK-，照抄示例的人必然踩坑**（v3.1.1 已把占位目录改名为 `task-NAME`）。
>
> **其余命名沿用文件已有的大小写**：文件名用中文 / 大写前缀（`PHASE-` / `BLUEPRINT-` / `HUMAN-` / `模板-`），
> 只有**目录名**（`methodology/`、`task-<任务名>/`）一律小写。
> **不要用**「PHASE-3-执行合并.md」这类**主题名不表明文档类型**的写法——
> 它让「这是蓝图还是报告」只能靠打开文件才知道。（历史遗留，不再新增。）

### 3.3 目录分离：方法论 与 任务 必须分目录（**v2.2 新增，硬要求**）

**两个目录，职责互斥**：

| 目录 | 放什么 | 跨任务复用 |
|---|---|---|
| **`methodology/`**（小写） | 规范、经验库、回写规范、文档模板、读取指令 | ✅ **整体拷到另一个任务，无需改动即可用** |
| **`task-<任务名>/`**（**小写** `task-`） | 总蓝图、阶段蓝图、完成报告、决策/审计文档、该任务的人工台账 | ❌ 只属于这一次任务 |

**为什么必须分**：混在一起时，新任务的 agent 会读到**上一个任务的基线数值与已拍板决策**，
把别人的结论当自己的约束——这是"经验越用越错"的主要来源。

**读取指令：本体系只有一个 agent 身份 —— 撰写者**（不搞「按角色挑一行读」）：

| 身份 | 最小必读集 | 份数 |
|---|---|---|
| **撰写者** ★唯一身份 | ① `methodology/BLUEPRINT-撰写规范.md`（全文）② `methodology/BLUEPRINT-经验库.md`（通读一次）③ `task-<任务名>/BLUEPRINT-总蓝图.md` ④ **上阶段完成报告的「五、关键偏差」与「十、回写清单」两节** ⑤ 要写报告 / 决定回写去向时：`BLUEPRINT-回写规范与清单模板.md` | 4 份 + 上阶段报告 2 节 |

> 🔴 **旧版这张表有五行**（写蓝图的 / 执行阶段的人 / 写报告的人 / 写总蓝图的人 / 复核的人）。
> 拆成五行是错的：AI 读到自己属于其中一行，就以为**其余四行的活不归自己**。
> 实测原话是「**我的角色：写蓝图的人（不是执行者，也不是复核者）**」—— 三个「不是」全错。
> 现在合并成一行：**撰写者一人担四责**（写蓝图 / 复核 / 回写 / 维护总蓝图），**唯一不做的是施工**。

**跨目录引用一律用相对路径，不许写裸文件名**（裸文件名换目录后必然断链）：

```
从任务目录指向方法论：  ../methodology/BLUEPRINT-撰写规范.md
从方法论指向任务目录：  ../task-<任务名>/BLUEPRINT-总蓝图.md
同目录内互引：          直接写文件名（如 PHASE-4-完成报告.md）
```

**读取纪律（一句话，写进每份总蓝图抬头）**：

> **不要通读 `methodology/`。** 执行一个阶段只需 **3 份**（规范相关章节 + 总蓝图相关节 + 本阶段蓝图）；
> 经验库 `BLUEPRINT-经验库.md` 写蓝图前通读一次，之后按 §0 六问自检 + §8 场景速查回查；
> `BLUEPRINT-经验库-全量台账.md` 只用于考古。路径不存在时按本节规则**定位**，不要凭记忆猜。

**验收（本节的检验方式）**：

- 单独把 `methodology/` 拷到另一个任务的同级目录 → 无需改动即可用（跨目录相对路径的写法天然满足）
- 新会话**只读三份**（规范 + 总蓝图 + 本阶段蓝图）能独立执行一个阶段

**可移植性说明（照做即可）**：`methodology/` **不含任何指向包外文件的链接**——
任务侧的文件一律写成占位符（`../task-<任务名>/…`）；引用历史记录只写「**记录标识**」
（形如 `SELF-update 260925/<文件>:<行号>`、`task-仓库合并/<文件>:<行号>`，**不写成链接**）。
因此整个目录**拷到任何任务旁边都无需改动**。

**任务目录怎么建（新任务第一步）**：在 `methodology/` 的**同级**新建 `task-<任务名>/`，把三份模板各抄一份进去：

| 抄哪份模板 | 落成什么文件 |
|---|---|
| [模板-总蓝图.md](模板-总蓝图.md) | `BLUEPRINT-总蓝图.md`（索引 + 全局约束 + 已拍板决策 + 当前基线 + 判据台账） |
| [模板-施工蓝图.md](模板-施工蓝图.md) | `PHASE-<n>-<主题>.md`（每个阶段一份） |
| [模板-完成报告.md](模板-完成报告.md) | `PHASE-<n>-完成报告.md`（每个阶段一份） |
| —（**按 §4.1.2 的七列表自建**；不必等有人工环节，**开工前就把表头建好**） | `HUMAN-人工验证台账.md`（编号 H-nn，跨 Phase 累积，**每任务一份**；人工验证的**唯一载体**——作业单与回执并入其中，**不另建文件**） |

### 4.1 「人工环节」怎么写（**自 Phase 5 起必备**）

**它解决的现实问题**：被测对象里有**上游不知道其存在**的自建功能（本任务 11 项，官方树 0 命中），
**标准测试结构上抓不到它们的失效**；而且有些决策是**产品取向**，agent 不能替人做。
P0–P4 全自动，**P5 起人回到回路中**。

**四个时点的硬分工（v2.6 形成 H-A / H-F / H-B / H-C 完整矩阵，统一写进同一份台账）**：

| 类型代号 | 何时 | 性质与作用 | 不满足的后果 |
|---|---|---|---|
| **H-A 拍板** | Phase 开工**前** | **阻塞性决策**：未拿到答复不得开工（台账里以未勾选标记表达；**仅此一种时点允许用它**） | 违规者会做出不可回退的产品决定 |
| **H-F 验收** | 每个功能完成**后** | **功能级门禁**：确认真实功能在目标环境可用；**仅 `M` 档阻塞出口，`O` 档不阻塞**（§4.1.0） | 「代码写完」被冒充为「功能完成」 |
| **H-B 评审** | Phase 施工**后** | **阶段退出条件**：人只做全局判断项，确认本 Phase 整体可退出 | 全局遗漏或顺手删功能无法被发现 |
| **H-C 登记** | Phase 完成**时** | **欠账登记**：本 Phase 验不了的，追加进同一份台账的一行并进 BACKLOG | 欠账散落各处导致后续漏验 |

#### 4.1.0 「必验 / 选验」两档（**v3.0 新增，最重要的一条减法**）

一刀切地要求「每个独立功能都要人工验收」，会把吞吐锁死，最后的结果是**人开始糊弄台账** —— 比没有台账更糟。
真实的分界线不是「功能大小」，而是：**这件事的正确答案，机器能不能自己判定？**

| 档 | 判据（问自己） | 处置 | 是否阻塞 Phase 出口 |
|---|---|---|---|
| **M 必验** | 这个结论**必须有人看到一个真实结果**才能成立吗——真实外部渠道、真实设备、真实账号、真实支付、真实用户视角的「能不能用」 | 登台账 `H-nn` | **阻塞**：未闭合不得宣告完成 |
| **O 选验** | 机器判据已经能给出**同等强度**的结论，人只是「再确认一眼」 | 登台账 `H-nn`，`档` 列写 `O` | **不阻塞**：人不看就由机器结论关闭 |

**三条硬规则**：

1. **默认选 O。** 把一条升级为 M 必须写一句理由：「机器判不了，因为……」。**写不出理由的一律 O。**
2. **C 类（真实渠道 / 外部服务 / 真机）一律 M**，且必须在真实目标环境验，不许用 Mock、模拟消息、API 自测代替。
3. **O 档关闭必须留痕**：报告里写「由 A 类判据关闭」，不能默默当它通过了。

> 这一条不削弱「代码完成 ≠ 功能完成」（原则 5），而是把它的适用范围从「所有功能」收窄到「**机器判不了的功能**」。
> 原则 5 的原文同步按此口径理解：**M 档功能**才是「自测通过不等于完成」的对象。

**分档之后的四条纪律**：

1. **人只做机器做不了的事**：产品取向、视觉/交互确认、文案可读性。
   **不要让人重算脚本能算的数字** —— 那既浪费人的时间，也会掩盖真正的判断点。
2. **期望值必须由 agent 预先算出**（真实代码在数据副本上跑一遍），不能靠读代码推断、也不能让用户猜。
3. **无法人工验证时必须明说**（例：依赖未装、应用起不来）。
   ⚠️ **不要为了让本节"有内容"而发明无用的人工步骤** —— 让人去点一个跑不起来的程序是负价值。
4. **登记不等于完成**：H-C 的条目是本 Phase 的**欠账**，必须写进交接提示 + HUMAN 台账，
   在具备条件的 Phase（通常是 P8）逐条销账，**未销账不得宣告任务完成**。

**回执要求**（**v2.4.1 改口径**）：**回执 = 台账里那一行**。
执行者执行者把 H-A 的答复**原样抄进**台账 `答复 / 结论` 列（并同样摘要进施工记录 §0，见 §8 子节 0），
H-B / H-C 同表登记。**完成报告不复制结论，只索引本 Phase 的 `H-nn` 清单**（避免同一结论两处维护）。
**没有回执（= 台账里那行没回填）的人工环节视为未执行。**

#### 4.1.1 人工验证的三类分工（A / B / C，**v2.4 新增**）

| 类 | 谁做 | 判据形态 | 前置不具备时 |
|---|---|---|---|
| **A 类** | **agent 独立完成**（不需要人眼） | 机器判据（命令 + 期望值 + 失败处置） | — |
| **B 类** | **必须人眼**：agent 负责把窗口开好、把期望值算好、把台账前四列填好；**人只判 ✅ / ❌** | "看起来对不对 / 能不能用" | **⏳ 待人眼**（不算失败） |
| **C 类** | 需要**真实渠道 / 外部服务 / 真机** | 端到端行为 | **🚫 无法验（缺 <具体缺什么>）** —— **不要填 ❌** |

> 🔴 **不要求人做机器能做的事**：A 类全部由 agent 跑；"让人重算脚本能算的数字"是负价值。
> **分类要与台账挂钩**：每条 B/C 项在 `HUMAN-人工验证台账.md` 里占**一行** `H-nn`
> （`类·档·时点` 列写 `B · O · H-B` 或 `C · M · H-F`，人只填后三列；例：`B-3 ↔ H-01`）。
> **A 类不登台账**（它由机器判据关闭，登进台账只会稀释台账的信噪比）。

#### 4.1.2 唯一载体：`HUMAN-人工验证台账.md`（**v2.4.1 重写**）

> 🔴 **一个人工环节只占一行；验证完成后就地回填那一行。**
> **人工验证台账继续保留，且职责不变**：`HUMAN-人工验证台账.md` 是人工验证的**唯一载体**。
> **绝对禁止新建平行文件**：不要因为新增了 H-F 功能级人工验收而建立 `功能验收.md`、`功能人工测试.md`、`人工验收回执.md`、`功能验证报告.md` 等。
> 每个功能级验收（H-F）直接在台账中占一行 `H-nn`，验完原地回写，功能状态随之更新。
> **为什么**：一次真实验收里，同一批人工项散在 **4 份**文档（台账 / 作业单 / 回执 / 逐类记录）——
> 人要同时开两个文件、agent 要维护两处状态，改一处忘一处就会出现"作业单让人做第 5 步、台账里只有 4 步"。

**七列，缺一不可。** 这张表是**唯一真值形态**，其余文档只准引用本表，不准复制列定义。

| 编号 | 类·档·时点 | 要验什么（点哪里 / 命令） | 期望值（agent 预先算出） | 状态 | 答复 / 结论 · 日期 | 证据 |
|---|---|---|---|---|---|---|
| **H-01** | C · M · H-F | <分组 → 项名 → 页面标题；界面原话逐字一致> | <实测数字或截图路径> | <⬜ / ✅ / ❌ / 🚫 / ⏳，见下> | <原样抄录答复；人只判 ✅/❌；未闭合的写去路 **H-nn → BACKLOG**> | <截图 `字节数 + sha256`；命令 + 输出> |

> **两条铁律**（细则见本节末「判据设计的八条硬要求」6–8）：
> **① 一台账一行**：一个人工环节只占一行 `H-nn`，作业单与回执都落在这一行里 —— **不另开文件**。
> **② 列归属固定**：`编号 / 类·档·时点 / 要验什么 / 期望值` **四列 agent 预填**；`状态 / 答复·结论·日期 / 证据` **三列人回填**（证据列 agent 可预填初值，人追加）。**没有无归属的列。**

> **`类·档·时点` 三段的取值**：
> `类` = `A`（机器）/ `B`（人眼）/ `C`（真实渠道·真机）；`档` = `M`（必验，阻塞出口）/ `O`（选验，不阻塞出口）；
> `时点` = `H-A` 开工前阻塞拍板 / `H-F` 功能级验收 / `H-B` 阶段完工评审 / `H-C` 欠账登记。
> **两档的判据与默认值见 §4.1.0**（经验库 §6 同一口径）。

**结论只有四种**（写在 `答复 / 结论` 列）：`✅ 通过` / `❌ 失败`（**必须附原始证据**）/
`🚫 无法验`（写清缺什么前置） / `⏳ 待人眼`。

> 📌 **「期望值」列就是作业单**：文首元信息（给谁 / 为什么 / 基线 / 硬约束）写在台账抬头的
> 区块里；「本次不验什么、为什么」与「还要你拍板的决策（不是验证）」**同样落在本文件**，
> 各自一个区块（`不验清单` / `待拍板`），不另开文件。
> 📌 **「证据」列就是回执**：既有台账实例里已有可用形态 —— 证据图
> `证据/H-01-H-05-顶栏与用量徽章-2026.png`、机器判据"11 项基线 `群上下文上限` 8 → **9**"、
> 计数"`0 failed | 562 passed (562)`"。
> 硬约束遵守自证（"**我没改任何东西**"）也写进结论列 —— 它同样是判断依据。

**判据设计的八条硬要求**（1–5 是判据本身，6–8 是**本行怎么填**；都是踩过坑换来的）：

1. **期望值由 agent 预先算出**（真实代码在数据副本上跑一遍），**不许让用户猜**；必要时把"登记时的实测值"整节快照下来，销账时逐条比对。
2. **对照物必须先就位**：否定型判据（"它**不该**说出 X"）在对照物为空时**通过得毫无意义**（经验库 **D33**）；
   台账要写明"对照物为空时该判据无意义，不得记为通过"。
3. **有数据风险的步骤设计成"只验门、不执行"**：例如"删除全部记忆"只验确认门（按钮初始是否禁用、错短语是否点不动），**验到就停手**；
   真要执行先做**外部备份**并把备份路径写进台账。
4. **"改开关 / 改配置"的步骤必须附验后复位**：验完回到默认态并读文件确认（经验库 **F19** —— 一次"成功的验证"曾把隐私开关留在打开态，含 3 个群）。
5. **两个变更源不叠在同一批验收里**：否则出问题无法归因。
6. **人工步骤写界面上的文案与路径，不写代码里的名字**：写「分组 → 项名 → 页面标题」+ **界面原话逐字一致**
   （从 i18n 取值粘贴）。实测：作业单写"设置 → 渠道"，界面那一页叫「**连接手机**」→ 一次真实的误判
   （经验库 **F21**）。改过文案的页面，台账要跟着改。
7. **前四列（编号 / 类·档·时点 / 要验什么 / 期望值）由 agent 预填完毕，该行才允许出现在台账里**：
   人只填后三列 `状态 / 答复·结论·日期 / 证据`。**不把机器能算的数、能自己跑的命令推给人**（人只做判断）。
8. **未勾选标记只用于 H-A**（阻塞拍板，开工前必须闭合）；B / C 类与 `O` 档一律用 `状态` 列取值（⬜ / ✅ / ❌ / 🚫 / ⏳）表达，
   **不许用未勾选标记**（否则 §5.1 那条「回写清单无未勾选项」的检查会把待验项误判成未回写）。

#### 4.1.3 验证完成后的销账：**原地回写同一个文件**（**v2.4.1 新增**）

**动作只有三个，都在同一个文件里完成**：

1. **回填那一行**：`状态` → `[x] 已闭合`（仅 H-A）或结论值；`答复 / 结论 · 日期` → 原样抄录；`证据` → 路径。
2. **追加，不改写**：证据后补时**保留原值 + 追加更正**（`~~旧~~ → 新` 或"更正：…"），不静默覆盖旧结论。
3. **未闭合的写去路**：`⏳ 转长期（BACKLOG-长期待办.md）` ／ `🚫 环境受阻（也进 BACKLOG）`。
   **不允许"未知"**：出现"未知 / 待定"就等于没登记。（也是一条可机械检查的判据 —— 但注意
   **判据别命中自己的原文**，经验库 **D29**。）

**部分销账要显式表达**（例："🟡 代码级已销账，运行期 5 步仍待 P8"），**不得用"已销账"盖住未验部分**。
**人工项没销完，不得宣告任务完成**（"结项 ≠ 全部人工项都销完"——未销的要进 BACKLOG 并写明触发条件）。

**回填后的三条机器判据**（作用域都已限定，不会自命中）：

```powershell
$L = "..\task-<任务名>\HUMAN-人工验证台账.md"
Select-String -Path $L -Pattern '^\|.*\[ \]'                       # ① 期望：无输出（无未闭合的 H-A 拍板）
Select-String -Path $L -Pattern '未知|待定|TBD' -SimpleMatch:$false # ② 期望：无输出（终态不含"未知"）
$L2 = "..\task-<任务名>\PHASE-<n>-完成报告.md"
Select-String -Path $L2 -Pattern '^\|.*\[ \]'                      # ③ 期望：无输出（回写清单已闭合）
```

**下一阶段的前置条件因此是两条，不是一条**：上阶段 ① **回写清单无未勾选项**，② **台账无未闭合拍板**。
第一条挡住"修正只活在报告里"，第二条挡住"拍板没答复就开工"。

> 台账：`task-<任务名>/HUMAN-人工验证台账.md`（跨 Phase 累积，编号 H-nn，**每任务一份**）。
> 结构 = 抬头（含文首元信息 + `不验清单` + `待拍板`）+ **上面那张七列表**（H-A 拍板 / H-B 评审 / H-C 待验
> **共用一张表**，靠 `类·时点` 列区分）+ 证据与更正区块（需要时）。
> 既有实例已证明这种形态可承载全部内容：单文件累计 **H-01…H-22**（含 5 次拍板、逐条期望值、
> 截图证据、`部分销账` 与 `转 BACKLOG` 去路），**没有另开作业单也能跑完一次完整验收**。

**「非目标」与「有意保留台账」的区别**（实战验证过的分工）：

| | 非目标 | 有意保留台账 |
|---|---|---|
| 何时写 | 施工**前** | 施工**后** |
| 内容 | 本 Phase 决定**不做**的事 | 施工中确认**故意维持现状**的点 |
| 作用 | 防止 agent 越界施工 | 防止**后续 Phase 重新论证**同一件事 |

两者都要有，不能互相替代。

## §5 完成报告必备结构（**10 节**）

> 骨架取自实战中已收敛的形态（P3/P4 逐节一致）。**报告不是蓝图的复述，是"实际发生了什么"。**
> **v2.2 起为 10 节**：原 9 节 + 新增「**十、回写清单**」（见 §5.1，**未勾完不得提交**）。

```markdown
# Phase N 完成报告：<名称>

> **状态**：✅ 已完成 / ⚠️ 部分完成 / ❌ 失败
> **执行日期**：
> **执行者**：agent（无对话历史，仅凭 [PHASE-N-….md] + [BLUEPRINT-总蓝图.md]）
> **结论**：一句话，含关键数字
> **报告规范**：见 `../methodology/BLUEPRINT-撰写规范.md` §5

## 一、执行摘要
   - 表格：每个验收项 → 结果
   - 「验收总计」：N 项主判据 PASS / FAIL 计数

## 二、最终状态（交接给 P<N+1>）
   - 代码块：关键标识（HEAD / 冲突数 / 快照 / 未提交与否 …）
   - 产出物表格：文件 → 内容 → 规模

## 三、执行过程（含命令与实测输出）
   - 按步骤复述**实际敲的命令**与**实际输出**（不是蓝图里的计划命令）

## 四、验收测试逐项结果
   - 表格：# / 验收项 / 期望 / 实测 / 判定
   - 每项的逐项实测输出（代码块）

## 五、关键偏差与判定修正（**给后续 Phase 必读**）★
   - 逐条：现象 → 根因（实测，非推断）→ 判定 → 对后续的影响
   - **判据本身的修正**也写在这里，并同步进 §7 判据台账

## 六、已知坑的实测复现情况
   - 表格：坑 / 本次是否复现 / 说明
   - **本次新踩到的坑**：单列一节，写明"建议追加进经验库"

## 七、回退方法（已验证可用）
   - 只写**本次实测验证过**的回退路径

## 八、给下一个 Phase 的交接清单
   - 编号清单；🔴 标必读；每条都要能被下一个 Phase 直接消费（路径、命令、判据）

## 九、Phase N 目标达成核对
   - 表格：目标（来自蓝图 §一）→ 状态
   - **非目标遵守情况**：逐条确认没越界

## 十、回写清单 ★（**v2.2 新增；未勾完不得提交**）
   - 四列表：触发条件 / 回写目标 / 回写内容一句话 / 已勾选
   - 四类触发（T1 判据被修正 / T2 基线数值被改写 / T3 蓝图描述被实测推翻 / T4 新增一条经验）
     逐条过一遍；**无触发的写"无"**，不许留空
   - 规则：**只新增 + 标注，不静默删除**；旧值留在原地或移入「历史基线」
```

**十节之后是三类追加节，编号接续、不许跳号**：

| 编号 | 节名 | 谁填 | 何时必填 |
|---|---|---|---|
| **十一** | 人工环节回执与功能验收闭合 | 执行者 | 本 Phase 有人工环节时（含全部 `O` 档） |
| **十二** | 施工记录（见 §8） | 执行者 | 总是 |
| **十三** | 撰写者复核补正（见 §5.2） | 撰写者 | 总是（结项 Phase 也必须有） |

> 🔴 **自 Phase 5 起（或任何涉及新增/修改独立功能的 Phase），报告必须给出「功能级人工验收闭合情况」与「人工环节回执」**
> —— **v2.4.1 改口径：报告只写索引，不复制结论**：
> 逐条列出**本 Phase 产生的 `H-nn` 编号 + 状态**（① H-A 答复的**原样抄录**留在台账 `答复 / 结论` 列；
> ② H-B 每条核对项的结论同表；③ H-C 已登记进台账的编号）。
> **缺台账行 = 该 Phase 不能判定为完成**；报告与台账**不得各存一份结论**（两处维护必然漂移）。
> 参考形态（既有实例）：`H-17 目视 5 步 → ⏳ 待验（P9 退出条件）`、`H-20 = ✅ 已拍板 A（答复原文「AA」）`、
> `H-19 → 🟡 部分销账（机器判据全绿、人眼项待复验）`。

### 5.1 修正回写（**v2.2 新增，硬要求**）★

**要解决的问题**：修正只活在完成报告里，主蓝图仍是旧口径 → 下一个 Phase **必须回头翻旧报告**才知道该按哪版执行。
一旦有第二份报告，口径就开始互相矛盾。

**四类触发（任一出现即必须回写）**：

| 编号 | 触发条件 | 回写目标 | 回写动作 |
|---|---|---|---|
| **T1** | 判据被修正 | **判据台账**（总蓝图 §9.1，或该任务的独立台账） | 追加一行：旧判据 / 新判据 / 依据（哪份报告的哪条偏差）/ 生效范围 |
| **T2** | 基线数值被改写 | 总蓝图「**当前基线**」 | 写新值；**旧值移入「历史基线（仅存档）」**，不删除 |
| **T3** | 蓝图描述被实测推翻 | 总蓝图对应节 | 就地改正 + 保留「**曾错、已修正**」说明（含依据报告） |
| **T4** | 新增一条经验 | [BLUEPRINT-经验库.md](BLUEPRINT-经验库.md)（**唯一经验库**，按失效类别归入 P/B/V/C/R/H/I 某节） | 三段（反例 / 为什么会错 / 怎么才对）+ 键号续编 + 括注旧版键号 |

**动作要求**：

1. 完成报告末尾必须有「**十、回写清单**」——四列：`触发条件 / 回写目标 / 回写内容一句话 / 已勾选`，
   **未勾选完不得提交**。
2. 下一阶段的前置条件加一条：**上阶段回写清单无未勾选项**。

   **检查命令只有一处定义**，以本节为准（其余文档一律引用本节，不许各写一份）：

   ```powershell
   # 期望：无输出。作用域同时覆盖「列表式 - [ ]」与「表格行 | [ ] |」两种写法
   Select-String -Path "..\task-<任务名>\PHASE-<上阶段>-完成报告.md" -Pattern '^\s*-\s*\[ \]|\|\s*\[ \]\s*\|'
   ```

   🔴 **这条命令必须配一次负向对照**（经验库 **P13**）：拿一份**故意留一个 `[ ]` 的样例报告**跑一遍，
   **必须命中**；命中不到就说明命令本身失效（旧版只匹配 `- [ ]`，而清单实际是表格行 →
   4 项全未勾也会「无输出」，等于门禁根本没开）。**没做过负向对照的判据不得写进门禁。**
3. **回写只「新增 + 标注」，不静默删除**：旧值留在原地，或移入「历史基线」段落。

> 完整定义、话术与可直接抄的清单模板见 **[BLUEPRINT-回写规范与清单模板.md](BLUEPRINT-回写规范与清单模板.md)**。

**验收（本节的检验方式）**：

- 新会话**只读「规范 + 总蓝图 + 本阶段蓝图」即可正确执行** —— 不需要回头读任何旧阶段报告来纠正口径
- 若发现"必须翻旧报告才对"，说明有一条回写漏了：补回写，而不是在报告里加导航

### 5.2 撰写者复核补正（**双角色分工，v2.4 新增**）★

**前提**：**写蓝图的人**与**执行蓝图的人**是两个 agent（撰写者**不参与施工**）。
**每个 Phase 交付后，撰写者独立复核**，并把结果作为一节追加到该 Phase 的完成报告里
（各 Phase 顺延编号：§十一 / §十二 / §十三…）。

**复核方式（写进抬头）**：

> 复核人：撰写者（未参与本 Phase 施工）
> 复核基线：`<提交哈希>`（tag `<tag>`）
> 复核方式：**不采信报告自述，逐条独立复跑**；关键判据**用与执行者不同的机制独立重写**
> 总结论：采信 / 不采信；N 项判据逐条复现；下面 M 处补正

**小节清单（可直接抄）**：

| 小节 | 作用 |
|---|---|
| ★.1 我独立复现的断言 | 表：**报告断言 / 我的独立实测 / 判定**（逐条对得上） |
| ★.2 补正 · 口径类 | 同一个数在不同口径下都"正确"（如差异行数带不带 `--ignore-cr-at-eol`） |
| ★.3 补正 · 计数类 | 数法/口径缺失导致**不可复现**（并注明"实质结论是否受影响"） |
| ★.4 补正 · 观察项 | 非缺陷，但会误导后续（如判据覆盖边界之外的同类残留） |
| ★.5 **复核者自身造成的漂移** | 主动认领（如工作区 `??` 计数变化），别让后人误判成异常 |
| ★.6 报告未覆盖、由复核补上的新发现 | 登记 **H-nn**，并**归因到判据缺口**（"不是执行者的过失"） |
| ★.7 等价改写逐条定性 | 把"只动了 X"这类笼统声明拆成清单（有无可见影响） |
| ★.8 上一 Phase 遗留 / 顺带发现 | 不可达分支、死键、自我抵消的改动 |
| ★.9 **文档回写复核** | 索引是否陈旧 / 抬头计数是否自洽 / 交叉引用是否失效 |
| ★.10 本次复核的环境教训 | 复核者自己踩的坑（也要进经验库） |
| ★.11 追加（下一 Phase 期） | 人眼结果、时点之后才出现的证据 |
| ★.12 复核结论与出口 | 六行判定表：施工质量 / 功能面 / 判据成立性 / 文档回写 / 遗留转下一 Phase / 出口条件 |

**它买到什么**（都来自实测）：

- 拦下"**两个口径相减**"造成的假警报（同一个提交的两组差异数字，差 23 个文件，**只差行尾**）；
- 把脆弱判据升级为可机械判定的等价物（**"数行数" → "比 blob 哈希"**）；
- 区分「**数字不可复现**」与「**结论错误**」（前者只降结论强度，后者要返工）；
- 让"**无功能影响**"这句话第一次有证据（事件处理器 8/8、4/4、10/10 逐字仍在）；
- 把"全绿"从「判执行者对错」改成「**判判据缺前提**」（环境指纹 + 四步归因，见下）。

**四步归因法**（复核发现"红"时必须走完才能定性）：**(a)** 失败面是否落在本 Phase 改动面内
（`git diff --stat <base> <head> -- <该目录>` 是否为**空**）；**(b)** 隔离复现（单跑该文件是否仍红）；
**(c)** **机制命中**（工具捕获的 `stderr` 字节数与手工复现的字节数是否吻合）；**(d)** 修环境后是否转绿。

> 🔴 **结项 Phase 也必须复核**：实测有一份"结项报告"缺这一节，而它恰好是**执行者自己在回写时吃掉一行台账**的那个 Phase。
> **越靠近收口，越需要一双没参与施工的眼睛。**

### 5.3 核验报告与缺陷报告（**v2.4 新增**）

**保真核验报告**（`PHASE-<n>-<主题>核验报告.md`，合并 / 迁移 / 大规模重构类任务必备）：

- **分层机械口径**：**文件层 → 符号层 → 入口层 → 桥接层**。一句话原则：**"文件在 ≠ 内容在 ≠ 入口在"**。
  每层都要有可复跑命令与数字（例：35 个本地新增模块的引用数前后对比，**2 项由 ≥1 降为 0** = 入口丢失）。
- **参照物先校准**（经验库 **D26**）：先证明"拿哪个快照当基线"，再谈结论；不可用的参照物要**写明为什么不可用**。
- **残余不确定性必须显式声明**：机械证明不了的部分（如"双方都改过的 822 条路径无法逐行证明语义"）要写成
  「这是本次核验**最大的残余不确定性**」，并列出**代理覆盖**（符号层 / 入口层 / 功能基线 / 行为探测器）。

**缺陷报告**（`缺陷报告-<编号>-<一句话>.md`，安全 / 隐私 / 数据类缺陷**单独立项**）：

| 节 | 内容 |
|---|---|
| 一句话结论 | 是"功能损坏"还是"**能力在、入口没了**"这类定性要一次说清 |
| 现象 | **使用方反馈 vs 实际**（谁报的、报的是什么、代码里实际是什么） |
| **三层对照** | 后端 / 桥（IPC、preload）/ 渲染层，逐层给**决定性核验命令** |
| 影响 | 阻塞了哪些判据 / **未造成的影响**（防止过度反应） / 🔴 **数据安全提示** |
| 建议处置 | 最小改动 + 路线权衡 + 可复用件 |
| 复现命令 | 可直接粘贴执行 |
| 逐层定界 | 表 + **已排除的点**（证明不是别的原因） |
| 修复与验证 | 改动表 / 实测数字 / **决定性反证** / 唯一残留 / 建议后续 |

- 🔴 **安全 / 隐私类缺陷不要塞进"小修"**：**行为变更 + 无测试覆盖 + 安全关键**，三者叠加时
  应当**登记立项**（登记 `H-nn` + BACKLOG），而不是顺手改在当次收尾提交里（经验库 **A50**）。
- **修复必须配一条"能变红"的回归测试**，并用**故障注入**证明它真的能抓住这个缺陷（经验库 **F17**）。

### 5.4 Phase 出口条件升级与推进规则（v2.6 核心推进模型）

#### Phase 出口九项条件（缺一不可）

一个 Phase 只有同时满足以下九项条件，才能进入「已完成」状态：

| # | 条件名称 | 具体要求 |
|---|---|---|
| **①** | **施工目标全部达成** | 蓝图 §一 规划的目标清单逐项达成，非目标未越界 |
| **②** | **机器验收全部通过** | 蓝图 §六 的自动化测试用例（A-nn）全量 PASS，命令输出吻合 |
| **③** | **所有 M 档功能人工验收通过** | 「功能级完成清单」中所有标 `M` 的功能均达到 `✅ 人工验证通过`；标 `O` 的功能已由 A 类机器判据关闭并留痕 |
| **④** | **H-B Phase 完工评审通过** | 人类完成本 Phase 的全局退出评审，并在台账对应行完成回填 |
| **⑤** | **HUMAN 台账无未闭合的阻塞项** | 台账中不存在未闭合的 H-A，也不存在未闭合的 **M 档** H-F / H-B；无未知状态。`O` 档未闭合**不阻塞出口** |
| **⑥** | **完成报告编制完成** | 完成报告涵盖全部 10 节必备内容，含真实命令与实测输出 |
| **⑦** | **T1–T4 回写清单全部闭合** | 完成报告 §十 回写清单无未勾选项（用 §5.1 那条**唯一命令**检查，且该命令已通过负向对照） |
| **⑧** | **撰写者独立复核完成** | 撰写者独立复核并完成 §十三 复核补正，明确给出允许出口结论 |
| **⑨** | **总蓝图已经同步** | 总蓝图最新基线、决策与修正已回写完成，口径已对齐 |

> 🔴 **功能人工验收是 Phase 完成的必要条件之一，而不是 Phase 完成后的附加工作。**

#### Phase 之间的完整推进流程

```
           总蓝图
             │
             ▼
      生成 Phase N 蓝图
             │
             ▼
        执行 Phase N
             │
             ├── 功能 F1 ──→ 自动测试 ──→ 人工验证 (H-nn) ──→ 台账原地回写 ──→ 功能完成
             │
             ├── 功能 F2 ──→ 自动测试 ──→ 人工验证 (H-nn) ──→ 台账原地回写 ──→ 功能完成
             │
             └── 功能 F3 ──→ 自动测试 ──→ 纯机器逻辑（无需人工）──────────────→ 功能完成
             │
             ▼
       Phase N 全部功能闭合
             │
             ▼
       H-B Phase 完工评审
             │
             ▼
          完成报告
             │
             ▼
       T1–T4 修正回写
             │
             ▼
       撰写者独立复核
             │
             ▼

             │

       Phase N+1 施工蓝图
```

#### 明确禁止事项（八大红线）

- ❌ **Phase N 施工中，同时生成 Phase N+1 施工蓝图**；
- ❌ **功能代码写完 → 直接标记为功能完成**；
- ❌ **自动化测试通过 → 直接标记为功能完成**；
- ❌ **Agent 自己模拟外部渠道（如模拟 QQ、Mock API）→ 代替真实渠道人工验证**；
- ❌ **Phase 结束时一次性让人把所有 M 档功能扫一遍 → 代替功能完成后的即时人工验证**；
- ❌ **新建独立「人工验证文件」或「功能验收报告」替代 `HUMAN-人工验证台账.md`**；
- ❌ **人工验证失败，但因为 Phase 其他自动化测试通过而宣告 Phase 完成**；
- ❌ **M 档人工验证因环境无法执行，却把功能标记为完成（必须标 🚫 / ⏳ 并入 BACKLOG）**。
- ❌ **把机器完全判得了的功能硬升成 M 档**——用人工掩盖「判据没写出来」，是本体系最容易退化成形式主义的地方。

## §6 总蓝图的职责与同步义务

总蓝图 = **索引 + 全局约束 + 已拍板决策 + 当前基线**。它不含具体步骤。

必备内容：

| 区块 | 内容 |
|---|---|
| 任务背景 | 一句话 + 关键拓扑（决定策略，不可搞错） |
| 成功判据 | Definition of Done，逐条可验 |
| 全局约束 | 工具边界 / 环境陷阱 / 每步可验证 / 提交粒度 |
| Phase 索引 | 表格：Phase / 名称 / 性质 / 风险 / 状态 / 文档链接 |
| 依赖关系 | 为什么不可跳过（硬依赖理由） |
| **已拍板决策** | 「Agent 不得重新论证」的决策表 + 依据文档 |
| 必须保护的东西 | 基线文件 + 逐项清单（标准测试覆盖不到的部分） |
| 参考文档索引 | 本目录（`task-<任务名>/`）+ **方法论目录**（`../methodology/`：规范、经验库、回写规范、模板），全部用**跨目录相对路径** |
| **当前基线** | ✅ 最新，供逐项比对；历史基线折叠为"仅存档" |
| 回退手册 | 分级回退命令 |

### 同步义务（硬要求）

- 每个 Phase 收到的是**总蓝图 + 该 Phase 蓝图**两个文件 → 总蓝图里的错误会**污染每一个 Phase**
- 因此：**实现过程中发现总蓝图需要修改时，必须回写总蓝图**（触发条件与动作见 §5.1 的 T1–T4）
- 总蓝图必须标出**它自己错过的地方**（例：`> ⚠️ 本节曾有两处错误，已修正`）——这是可信度的一部分，不是丢脸
- 总蓝图的「当前基线」被新 Phase 取代时，旧值**移入"历史基线（仅存档）"**，不要直接删
- **总蓝图抬头必须写一句读取纪律**：不要通读 `methodology/`；按 §3.3 的最小必读集读

## §7 判据台账（判据会错，且必须留痕）★

### 7.1 充分判据 vs 启发式指标

写验收项时必须自问：**这条命令真能证明我想证明的事吗？**

| 类型 | 例子 | 判定力 | 要求 |
|---|---|---|---|
| **充分判据** | 退出码为 0、`JSON.parse` 成功、`diff` 为 0 行、目标 id 命中数 = 0 | 强 | 直接可用 |
| **启发式指标** | `Select-String` 命中数 ≥ 1、`findstr` 命中文件数 ≥ 基线 | **弱**（计数不证明内容正确；只删文件不算逻辑也会让计数退化） | **必须配一条交叉验证**，或明确标注为"代理指标" |

> 实战教训：某个 `grep "qq:<id>"` 的判据**结构上抓不到**某类残留（向量条目里存的是**裸** id，
> 没有渠道前缀）。判据的形状决定了它能看见什么——写的时候就要想清楚这一点。

### 7.2 判据台账格式（跨 Phase 累积）

判据一旦被修正，必须在两处留痕：**完成报告 §五** + **总蓝图 §9.1 或独立台账**（编号累积）。
（骨架见 [模板-总蓝图.md](模板-总蓝图.md) §九.1；本节定义的是**格式**，放哪由任务自己定，但**必须有**。）

| 编号 | 旧判据 | 新判据 | 依据（哪个 Phase 的哪条偏差） | 生效范围 |
|---|---|---|---|---|
| J-01 | 未跟踪文件数 ≥ 141 | 逐项核对工作资产是否仍在磁盘上 | P3 偏差 2（判据与步骤自相矛盾） | P3 之后 |
| J-02 | 其余 10 项功能基线不得退化 | 退化必须能归因到本 Phase 主动删除的文件 | P4 偏差 3（删文件必然让"仅存在于被删文件"的标识退化） | P4 之后 |
| J-03 | grep 出的每一处 `<id>` 都落在 `subjectIds` 里 | 同上，但 **`memory-trace.log` 例外**（它是删除动作的审计载体） | 手工验证第 6② 条 | 该任务之后 |

**必须写成台账的理由**：修正散落在各份完成报告里，后续 Phase 得翻遍所有报告才知道该按哪版验收。

**台账维护的四条硬动作（v2.4，都是踩过坑换来的）**：

1. **只新增、不删除**：旧判据留在原地——它记录的是"**曾经按什么验收**"，删掉就再也看不出口径为什么变过。
2. **追加型编辑必须把锚点行原样写回**：`new_string` 要**完整包含** `old_string` 的内容再追加（如 `old + "\n" + new`）。
   实测事故：追加 `J-36/37/38` 时把 **`J-35` 整行吃掉**，而**表格外观依然连贯**（J-34 下面直接接 J-36），肉眼看不出来。
   长行表格还容易**误替换相邻行** —— 更稳的做法是**按编号整块重写**，而不是逐条插入。
3. **改完立刻做"连续性 + 结构"校验**（最便宜的完整性门禁）：
   - **编号无缺号**：取出全部 `J-nn`，与 `1..N` 求差集 → **期望为空**；
   - **表格列数一致**：把转义 `\|` 还原后逐行数有效列数 → **异常行 = 0**；
   - **行数比对**：改前 N 行 → 改后应为 N+k 行，**对不上就是吃掉了东西**。
4. 每条新判据**四要素齐备**：`旧判据 / 新判据 / 依据（哪个 Phase 的哪条偏差 + 实测数字）/ 生效范围`。

> 🔴 **同族的"收尾判据自命中"陷阱**：用字面搜索检查"台账里不许有『未知』/ 不许有未勾选"时，
> **判据的原文自己就含那个字符串** → 要么恒失败、要么被人为放宽到失效。
> 正解：**限定作用域**（只扫"状态"列 / `^\|.*\[ \]`），或改成**结构判据**（终态取值只允许 ✅/⏳/🚫），见经验库 **D29**。

> **人工验证的欠账用同级台账累积**：`task-<任务名>/HUMAN-人工验证台账.md`（编号 **H-nn**，自 P5 起生效）。
> 判据台账管"**按哪版验收**"，人工台账管"**还欠哪些人要做的事**"。两者都要有。
> **各任务自己的一份**：台账属任务专属，新任务在 `task-<任务名>/` 下另起一份，不要复用别人的欠账清单。

### 7.3 三类必须提前写明的"不算失败"

1. **时点断言**：擦除后主体又活动了 → 断言自然失败。判据要写"取值于**动作刚完成的那一刻**"
2. **有意保留项**：预先声明保留的东西出现在扫描结果里，不算残留
3. **外部增长量**：别的进程在写（语料、审计行数）→ 给容差，或改成"只允许纯追加"的相对判据

### 7.4 长期待办（`BACKLOG-长期待办.md`）

**它解决的病灶**：范围裁剪、"顺手发现的低优先项"、"以后再说"的决定，一旦只写进完成报告或对话，
就等于**失踪**（经验库 **C16**）——下一轮没人知道它们存在。

- **每条四个字段**：`编号 / 内容 / 谁做 / 触发条件`。触发条件写"**什么时候必须做**"，不写"尽快"。
- **状态取值**：`⬜ 未做 / 🔄 进行中 / ✅ 已完成 / 🚫 不适用` —— **不允许"未知"**（出现"未知"就等于没登记）。
- **验收**：该文件里 grep 不到"未知 / 待定 / TBD"；每条都能回答"下次谁在什么条件下接着做"。

### 7.5 有意放弃清单（`ABANDONED-有意放弃清单.md`）

**它解决的病灶**：范围裁剪与"取 ours / 取 theirs"的取舍若只留在报告里，后人会把它当"漏做"重新投入，
甚至把**故意保留的参照物**当垃圾清掉（经验库 **P3** 的假红就是这么来的）。

- **每条四件事**：*放弃什么（路径/符号级） / 为什么（依据） / 依据文档 / 将来要恢复怎么办*。
- **覆盖判据**：**「未归类 = 0」**。类别数**允许随对象增补**，不要拿"必须落到 N 类之一"当判据（经验库 **P11**）。
- **生成方式**：条目**机械生成**（脚本输出表格再注入文档），手抄必错。

### 7.6 上游同步（`SYNC-<主题>SOP.md`）

**适用**：任何"长期跟随一个外部上游"的任务（本轮合并之后，本项目的常态）。

1. **必须写明权威源与数据来源**：本地镜像 / 克隆只是**缓存**，不是权威源。同步结论必须同时输出
   「**源**」与「**新鲜度**（最后一次 fetch 的时间）」；缓存落后时**必须回源**，或把结论降级为"**未检查**"——
   **不许报"无风险"**。（真实病灶：脚本先读过期镜像，于是诚实地报告"上游无新提交 / RISK 0"，
   而真相是 **77 个提交 / 51 个撞车文件**。）
2. **RISK 是上界，不是工作量**：`双方都动过的文件数` 是保守上界；真实工作量要**试合并**量出来 ——
   在**独立临时 worktree** 里做（不碰主工作区、不产生提交、跑完即删），并把结果存成**进度基线**。
3. **周期性跑一条命令**：把 `--check` 的数字当**进度表**（例如每 7 天一次），"在缩小还是在拉大"一眼可见。

**判据**：`--check` 的输出必须含「**源 + 新鲜度 + RISK + 待合并提交数**」四项；缺任一项即**不可判定**。

## §8 施工记录（执行者追加的 §12）

> **原则**：遇到真实代码与蓝图冲突时，**以真实代码为准**。
> 本节由执行者在完成后追加，记录**与蓝图不一致处**及原因。

必备子节（按需增减，但 1/2/4/5 为必需）：

| 子节 | 内容 | 格式 |
|---|---|---|
| **0 人工环节回执**（**Phase 5 起必需**） | **本 Phase 的 `H-nn` 索引**：编号 + 状态；H-A 答复原文留在台账那一行（v2.4.1：**报告不复制结论**） | 三列表：`H-nn / 类·时点 / 状态`，骨架见 [模板-完成报告.md](模板-完成报告.md) 末节「人工环节回执」；**唯一真值在 `HUMAN-人工验证台账.md`** |
| **1 主进程 / 实际落地** | 逐条记录偏离 | 三列表：**蓝图 / 实际实现 / 原因** |
| **2 蓝图未覆盖、施工中发现的漏洞** | 蓝图漏掉的，一并修复 | 三列表：**位置 / 问题 / 修复** |
| 3 蓝图最大不确定点的核实结论 | 蓝图自己标注的疑问，施工后给答案 | 引原文 + 结论 + 证据 |
| **4 有意保留的"不处理"点** | 故意维持现状的，附理由 | 清单，每条给"为什么不管" |
| **5 验收（实测数字）** | 门禁命令 + 实测值 | 表格：命令 / 结果 |
| 6 验收后修复 | 交付后才发现的，单开一节 | 现象 / 根因 / 修复 / 复验 |
| 7 经验追加 | 新坑 + 判据修正 | 见 §9，按 H/M/L 归位到经验库 |
| 8 待做 / 未做 | 如实列出，不给"已完成"的印象 | 表格：项 / 状态 / 说明 |

### 8.1 缺陷编号体系

发现的问题按 **D1、D2、D3…** 编号（观察类用 **O1、O2…**），每条必须给：

```
现象（什么命令/什么操作 → 观测到什么，带真实数字）
根因（机制层，不是"不小心"）
影响（谁会受害、多严重、会不会自愈）
修复口径（谁拍的板、按什么口径）
修复（改了哪些文件、判据是什么）
复现/证明证据（能独立复核的脚本或断言编号）
为什么以前没被发现（这一条最有价值——它决定同类问题还有多少）
```

> **「为什么以前没被发现」是必填项**。它直接回答"还有多少同类问题没暴露"。

### 8.2 手工验证记录（**v2.4.1：写进台账那一行，不在报告里另起一表**）

手工验证（需真人操作）必须留证 —— **载体是 `HUMAN-人工验证台账.md` 的那一行**（§4.1.2 的七列表），
**不是报告里的一张平行表**：同一批数据两处维护，必然出现"报告 5 步、台账 4 步"。

报告里只写**本 Phase 的 `H-nn` 索引**（编号 + 状态）；需要展开时引台账那一行。
若确需在报告里给一条**过程复述**（例如现场发现的意外），照下面四列写，并**同时**回填台账：

| 步骤 | 期望（权威来源） | 实测 | 判定 |
|---|---|---|---|
| <对应 `H-nn`> | <期望值来自哪条命令 / 哪次实跑> | <原样粘贴输出> | ✅ / ❌ / 🚫 / ⏳ |

- **期望值必须由"真实代码在数据副本上跑一遍"产出**，不能靠读代码推断（§4.1 判据设计硬要求 1）
- 每个"不算失败"的情形提前写明
- 差异必须归因到**具体哪一侧错了**——包括**验证工具自己错了**（见经验库 **V11**「验证工具自身必须被验证」）
- 回填是**追加**，不是覆盖：旧结论保留、新结论标注（§4.1.3）

## §9 经验库的用法与追加义务

**只有一个经验库：[BLUEPRINT-经验库.md](BLUEPRINT-经验库.md)。**

> **v3.0 的改动理由（实测）**：旧版拆成三份（通用 / 具体坑 / 全量台账，合计 33 万字符、约 186 + 74 条），
> 设计初衷是"按角色取最小必读集"。实测结果是——**agent 在任务中途不会回头翻库**。
> 那么在任务开始前塞进 5 万 token 的经验库，换来的不是"防住坑"，而是"上下文被吃掉一半"。
> 所以收敛为**一份小而全的库**：**能一次读完**是它的第一要求，**能查到一切**不是。

**怎么用**：

1. **写蓝图前整份读一遍**（约 2 万字符 / 106 条，通读成本可接受）——只做这一次通读。
2. **写判据 / 写蓝图 §六 / 写完报告自检时**，回到 §0「六问自检」并按 §8 场景速查定位到具体条目。
3. 蓝图「九、已知坑」写**与本 Phase 相关**的条目编号 + 本次复现情况，**不复述全文**。
4. **每次施工发现新坑，追加进经验库**（不是只写进完成报告），按失效类别归入 P/B/V/C/R/H/I 某节。
5. 每条经验**三段**，缺一不可：

```
反例（会怎么做错，具体到命令 / 代码 / 文档措辞）
为什么会错（机制层，不许写"不小心"）
怎么才对（可执行）
```

6. **经验的价值排序**（越靠前越珍贵）：
   - ① **被实测推翻的原计划**（"我们本来打算…，实测证明零收益"）
   - ② **判据自身的缺陷**（"这条断言结构上抓不到它"）
   - ③ **验证工具的缺陷**（"我的副本漏拷了一个文件，差点误判成产品缺陷"）
   - ④ 环境与命令坑（`2>&1`、编码、非 ASCII 路径…）

7. **库容量纪律**：上限约 90 条。超了先删——删依赖具体版本 / 项目的，删已被更抽象条目覆盖的。
   **没人读的经验库等于不存在。**

> ⚠️ **不要把具体结论当通用知识套用**：I 节条目（基础设施坑）的命令与 API 结论**只在那套技术栈成立**。

> ⚠️ **不要把具体结论当通用知识套用**：L 级条目里的命令与 API 结论**只在那套技术栈成立**。
> 换栈后要重新验证，不能照搬（这也是拆成两库的原因）。
