# 蓝图规范包 · 使用说明

> **这是什么**：一套"让 AI agent 写出可执行蓝图"的方法论。**规范本体 + 分级经验库 + 回写机制 + 三份文档模板。**
> **怎么用**：把 **`methodology\`** 整个文件夹丢给 AI，让它读。就这么简单。
> **目录已分离**：`methodology\`（跨任务复用）与 `task-<任务名>\`（本次任务专属）**互不污染**；
> 任务目录**不随本包分发**，用包里的三份模板在 `methodology\` 同级新建（见 `methodology\_先读这份-READ-FIRST.md` §三.1）。

## 一、这个包里有什么

```
蓝图规范-共享版\
├── methodology\                      ★ 方法论：给 AI，整个文件夹直接投喂，不用拆
│   ├── _先读这份-READ-FIRST.md             读取指令：按角色给最小必读集 + 任务目录怎么建
│   ├── BLUEPRINT-撰写规范.md               规范本体：蓝图 12 节 / 完成报告 10 节 / 判据台账 / 回写
│   ├── BLUEPRINT-回写规范与清单模板.md        T1–T4 触发条件 + 四列回写清单模板
│   ├── BLUEPRINT-经验库-通用.md             H + M 级经验（换语言/换同类系统仍成立）★写蓝图前必读
│   ├── BLUEPRINT-经验库-具体坑.md            L 级经验，按技术栈分章 —— 按栈检索，不通读
│   ├── BLUEPRINT-经验库-全量台账.md          全量 + 出处标识（溯源用，别整份读）
│   └── 模板-总蓝图.md · 模板-施工蓝图.md · 模板-完成报告.md    三份可直接抄的骨架
│
├── README.md                        ← 你正在读的这份（给人读；**文件名就是 `README.md`**，GitHub 会直接渲染）
├── 投喂说明-先读我.md                 可直接复制粘贴给 AI 的开场话术（给人读）
└── TASK-NAME\                       占位目录示例：把施工蓝图放进这里，或照它的位置建 `task-<任务名>\`
```

**本包有意不含两样东西**：

| 不含什么 | 为什么 | 你要用的时候怎么办 |
|---|---|---|
| **任务目录 `task-<任务名>\`** | 别人的基线与已拍板决策一旦混进来，就会变成你的约束——这是"经验越用越错"的主要来源 | 在 `methodology\` **同级**新建，用三份模板各抄一份（见 `methodology\_先读这份-READ-FIRST.md` §三.1） |
| **经验的原始存档** | 那是 30 万 token 级的历史记录，其中九成不需要读 | 不需要：经验条目**自身是完整的**（错误做法 / 症状 / 根因 / 正确做法四段齐全）；出处只承担"溯源"与"唯一标识"两个作用 |

**各部分的读者与分享方式**：

| 目录 | 给谁 | 分享时 |
|---|---|---|
| **`methodology\`** | AI（也能给人看） | **可以直接单独分享**——它自包含、**不含任何指向包外文件的链接**，拷到任何任务旁边都能用 |
| `README.md` · `投喂说明-先读我.md` | 人 | 建议一起给，尤其是给不熟悉这套方法的人 |

## 二、怎么用（一句话版）

**把 `methodology\` 整个文件夹拖给 AI，然后说**：

```
这个文件夹里是一套写蓝图用的规范与经验库。
请先读 methodology\_先读这份-READ-FIRST.md，按里面的"最小必读集"决定读哪几份，
读完告诉我你理解了、并复述你打算怎么做，我再给你任务。
```

AI 会自动只读该读的**2–3 份**（约 **4.5 万 token**；通用库请先查 §0 场景索引，命中再展开单条），不会去啃另外几份大的。
想要更精确的开场话术，用 **`投喂说明-先读我.md`** 里第二节的完整版——
它包含"先确认任务类型再动手""引用经验要用键号"等约束。

## 三、四种用法

| 场景 | 给 AI 什么 | 关键点 |
|---|---|---|
| **A 写一份新蓝图** ★最常用 | `methodology\` + 你这个任务自己的背景材料 | 规范给正面结构，经验库给负面清单，两者合起来就够 |
| **B 执行一份已有的蓝图** | 该任务的总蓝图 + 该阶段的蓝图（**就两个**） | **不要给规范和经验库全文**——执行者读得越少越不容易被带偏 |
| **C 迁移到自己的项目** | `methodology\` | 用规范 §1–§10 全部 + 通用经验库（H/M）全部 + 具体坑库**只取形状**；具体条目多为 Node/Electron 场景，**参考形状、别照抄结论** |
| **D 查证某条经验** | `methodology\BLUEPRINT-经验库-全量台账.md` | 约 **6 万 token**，**用关键词定位，别整份读** |

**场景 A 的完整话术**：

```
你现在的任务是【写蓝图】，不是执行。

输入：
1. methodology\BLUEPRINT-撰写规范.md —— 写作规范，你的蓝图必须满足它的 §4（12 节结构）
2. methodology\BLUEPRINT-经验库-通用.md —— H/M 级经验，写之前先过一遍 §0 场景索引
3. methodology\BLUEPRINT-经验库-具体坑.md —— 只查我这个技术栈的那一章，别通读
4. <你这个任务的总蓝图>
5. <当前阶段文档 / 上一份完成报告>（至少读它的「五、关键偏差」与「十、回写清单」）

请产出「阶段 N 施工蓝图」，要求：
- 严格按撰写规范 §4 的 12 节结构
- 「非目标」逐条给"为什么不做"
- 「实测证据」一节写：支撑决策的实测数字，以及**被推翻的原计划**
- 每条验收判据要能判定，并写明失败处置；区分「充分判据」与「启发式指标」
- 写完自检：经验库 §6 的四类通用形状，本蓝图有没有踩
```

**场景 B 的完整话术**：

```
你现在的任务是【执行阶段 N】，不是写文档。

输入：
1. <该任务的总蓝图> —— 全局约束与已拍板决策（不得重新论证）
2. <PHASE-N 蓝图> —— 本阶段的施工蓝图，自包含

要求：
- 先核对蓝图第 3 节的「前置条件」（含"上阶段回写清单无未勾选项"），不满足就停下报告
- 遇到真实代码与蓝图冲突时，**以真实代码为准**，并记录下来
- 出现第 3 节的「停止条件」时立即停止并报告，不要自行绕过
- 执行完毕产出「完成报告」，10 节结构：
  执行摘要 / 最终状态 / 执行过程 / 验收逐项结果 / 关键偏差与判定修正 /
  已知坑复现情况 / 回退方法 / 交接清单 / 目标达成核对 / **回写清单（未勾完不得提交）**
```

## 四、两个角色读的不是同一批文件（最容易搞混）

| 角色 | 读什么 | 产出 |
|---|---|---|
| **写蓝图的人 / agent** | 撰写规范 + 经验库-通用 + 该任务总蓝图 + 上阶段报告的「关键偏差」与「回写清单」 | 下一份 **阶段蓝图** |
| **执行蓝图的人 / agent** | 该任务总蓝图 + 该阶段蓝图（**只需这两个**；规范只查 §4/§5/§8/§10 相关节） | 执行结果 + **完成报告** |
| **写报告的人 / agent** | 同上 + `methodology\BLUEPRINT-回写规范与清单模板.md` | 完成报告 + **回写清单** |
| **复核的人 / agent**（撰写者） | 规范 §5.2 + 本阶段完成报告 + 总蓝图相关节（**不采信报告自述，逐条独立复跑**） | 报告里的「**撰写者复核补正**」一节 + 新的 `H-nn` |

- 执行者**不需要**规范和经验库全文。
- 写的人**必须读**当前阶段文档——很多坑是执行时才发现的，那份文档是唯一载体。

## 五、这套体系的三个机制（v2.2 新增，最重要）

### 5.1 方法论与任务分离

```
methodology\      跨任务复用 —— 整体拷到另一个任务旁边，无需改动即可用
task-<任务名>\    任务专属 —— 总蓝图 / 阶段蓝图 / 报告 / 决策 / 人工台账（**各任务自建**，见 §一）
```

**为什么**：混在一起时，新任务的 agent 会读到**上一个任务的基线数值与已拍板决策**，
把别人的结论当自己的约束——这是"经验越用越错"的主要来源。
**跨目录引用一律用相对路径**（`../methodology/…`），不许写裸文件名。

### 5.2 经验分级（H / M / L）

| 等级 | 判据（自评问句） | 放哪 | 读法 |
|---|---|---|---|
| **H** | 换一种语言还成立吗？→ 是 | `methodology\BLUEPRINT-经验库-通用.md` | 写蓝图前**必读** |
| **M** | 换同类框架还成立吗？→ 是（否 → L） | `methodology\BLUEPRINT-经验库-通用.md` | 写蓝图前**必读** |
| **L** | 核心是命令 / API 行为吗？→ 是 | `methodology\BLUEPRINT-经验库-具体坑.md` | **按当前技术栈检索，不通读** |

**避免的错**：把具体结论当通用知识套用。L 级条目只在那套技术栈成立，换栈要重新验证。

### 5.3 修正回写（**修正不能只活在报告里**）

| 触发 | 回写目标 |
|---|---|
| **T1** 判据被修正 | 判据台账（总蓝图 §9.1 / 规范 §7.2） |
| **T2** 基线数值被改写 | 总蓝图「当前基线」；**旧值移入「历史基线（仅存档）」** |
| **T3** 蓝图描述被实测推翻 | 总蓝图对应节；保留「**曾错、已修正**」说明 |
| **T4** 新增一条经验 | 经验库，**按 H/M/L 归位** |

- 完成报告末尾必须有「**回写清单**」四列表：触发条件 / 回写目标 / 回写内容 / 已勾选，
  **未勾选完不得提交**。
- 下一阶段前置条件含一条：**上阶段回写清单无未勾选项**（可 `grep` 验证）。
- **回写只「新增 + 标注」，不静默删除。**
- 🔴 **检查"有没有漏勾"不能全文搜 `[ ]`** —— 那一行判据自己就含这个标记；要限定作用域（`^\|.*\[ \]`）或改成结构判据。

### 5.4 双角色复核（v2.4 新增，来自一次真实合并）

**写蓝图的人**与**执行蓝图的人**是两个 agent；每个 Phase 交付后，**撰写者独立复核**并追加一节
「**撰写者复核补正**」到完成报告（规范 §5.2）。要点：

- **不采信报告自述**：逐条独立复跑；关键判据**用与执行者不同的机制重写**（机制不同 ⇒ 互为交叉验证）。
- **四步归因法**：出"红"时先走完 (a) 改动面是否为空 → (b) 隔离复现 → (c) 机制命中（`stderr` 字节数吻合）→ (d) 修环境后转绿，**再定性**。
- **它买到什么**：拦下"两个口径相减"的假警报、把"数行数"升级成"比哈希"、区分"数字不可复现"与"结论错误"、
  让"无功能影响"第一次有证据、把"全绿"从"判执行者对错"改成"**判判据缺前提**"。
- **结项 Phase 也必须复核**（实测最需要外部复核的，恰是执行者自己改台账的那一 Phase）。

配套的两类文档（规范 §4.1 / §5.3）：**人工验证台账**（人工验证的**唯一载体**——一个环节一行，
agent 预填「要验什么 / 期望值 / 证据」，人只填后三列，**验完就地回填、不新建文件**；v2.4.1）·
**缺陷报告**（安全 / 隐私 / 数据类缺陷单独立项，不塞进"小修"）。

## 六、经验条目的「出处」怎么读（分享场景必读）

条目末尾的「出处」是**原始记录的文档标识 + 行号**，两种形态：

```
① SELF-update 260925/phase3-p3-erasure-and-console.md:1622-1646   ← 8 份施工记录之一
② task-仓库合并/PHASE-2-完成报告.md:44                             ← 一次真实任务的完成报告
```

1. 它标识"**这条经验当时从哪份记录的哪几行抽出来**"，用于**溯源**；
   键号（C7 / D13 / R140…）本身也承担**唯一标识**，可被蓝图与报告直接交叉引用。
2. **这两类原始文档都不随本包分发**——所以出处**不是**包内的可打开路径，也不要去本包里找它。
3. **不解析出处完全不影响使用**：经验的价值**写在条目里**（错误做法 / 症状 / 根因 / 正确做法四段完整）。
4. 本包内**所有**跨目录引用都是相对路径（`methodology/…`、`../task-<任务名>/…`），任务侧一律是占位符，
   **不含指向包外文件的链接**——`methodology\` 可直接转发。
   ⚠️ **例外**：少数「环境类」条目会引用**原机器的绝对路径**（如 `D:\data\node24\npx.cmd`、`D:\data\node\npm.cmd`），
   那是**历史记录的原文**，用来描述当时那台机器的环境——**当举例看，不要照抄执行**，换成你自己的路径即可。

## 七、常见误用

| 误用 | 后果 | 正确做法 |
|---|---|---|
| 让 AI 通读 `methodology\` 全部 9 份 | 约 **13 万 token**，大半本轮用不上 | 按 `methodology\_先读这份-READ-FIRST.md` 的**最小必读集**读 2–3 份 |
| 把规范喂给**执行**者 | 执行者去纠结文档结构而不干活 | 只给总蓝图 + 阶段蓝图 |
| 写蓝图时不给上一份完成报告 | 重复踩已经踩过的坑 | 至少给上阶段报告的「关键偏差」+「回写清单」 |
| 只把文件夹丢过去、一句话不说 | AI 可能把"规范"当成"要执行的任务" | 用第二节 / 第三节的话术 |
| 拿 L 级经验的具体结论套别的技术栈 | 误伤无关代码 | 用**形状**自检，别照抄结论；L 级只在同栈复用 |
| 在本包里翻找"范例任务"或"证据存档" | 翻不到，白花时间，还可能误以为包是残缺的 | 任务目录自己建（§三.1）；**出处只是记录标识**，不是可打开的路径 |
| 把某个任务的总蓝图当模板复用给新任务 | 别人的基线与决策变成你的约束 | 换任务时用 `methodology\模板-总蓝图.md` 重写；只有 `methodology\` 才复用 |
| 修正只写进完成报告 | 后续阶段得翻遍旧报告才知道按哪版执行 | 按 T1–T4 **回写**，清单未勾完不提交 |

## 八、这是快照：怎么判断是否过期

**本包是某一时刻的快照，上游仍在演进。** 实测：本包生成前后 20 分钟内，
规范就从 v2.0 走到了 v2.1（蓝图 11 节 → 12 节、新增「人工环节」），某阶段文档从 501 行重写到 1054 行。

| 检查点 | 本快照的值 |
|---|---|
| 规范版本号（文件抬头 `> **版本**`） | **v2.4.1** |
| 施工蓝图必备结构 | **12 节**（含「五、人工环节」） |
| 完成报告必备结构 | **10 节**（+ 追加节：人工环节回执 / 施工记录 / **撰写者复核补正**） |
| 人工验证的载体 | **单文件 `HUMAN-人工验证台账.md`**（一个环节一行，九列表；验完**就地回填**，**不新建**作业单 / 回执——v2.4.1） |
| 经验库分级 | **H / M / L 三级**，拆为「通用」（H+M）+「具体坑」（L）+「全量台账」 |
| 目录结构 | `methodology\`（9 份）+ 包根两份人读说明（`README.md` · `投喂说明-先读我.md`）；**不含**任务目录与证据存档（§一） |
| 通用库条数 | **106**（H **67** + M **39**）★口径：表格行、按 ID 去重；历史值 56 → 80 → 106 |
| 具体坑库条数 | **74**（L；§1 git 7 / §2 Windows·PS 8 / §3 Electron·Node 9 / §4 TS·工具链 14 / §5 本项目 33 / §6 正则 3） |
| 全量台账条数 | **186 条**（R1–R186）+ 附录 B 的 10 条 X + **附录 E：v2.4 新增 70 条索引** |
| 通用形状 | **8 类**（原 4 类 + 相对引用语义漂移 / 静态检查盲区 / 判据形状错误 / **未被核验的前提**） |
| 新增文档类型 | 核验报告 / 缺陷报告 / 有意放弃清单 / 长期待办 / 上游同步 SOP（规范 §3.2；**验证作业单与回执已于 v2.4.1 取消**） |
| `methodology\` 文件数 | **9 份**（规范 / 回写规范 / 3 个经验库 / 3 个模板 / READ-FIRST） |
| 断链 | **0**（markdown 链接与路径型引用全部可解析；任务侧一律占位符；经验条目「出处」是记录标识，非链接） |

任何一项对不上，说明上游已经往前走了，请向分发者索取新版本。

**如果你在维护它**：本包是**分发产物**而不是**编辑对象**。
在上游仓库里改，然后重新生成整个包（保持同样的目录结构与路径映射）。
**不要**只手改包内某一份，那会让包内版本互相不一致。
