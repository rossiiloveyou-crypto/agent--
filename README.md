# 蓝图规范包 · 使用说明

> **这是什么**：一套"让 AI agent 写出可执行蓝图"的方法论。**规范本体 + 分级经验库 + 回写机制 + 三份文档模板。**
> **怎么用**：把 **`methodology\`** 整个文件夹丢给 AI，让它读。就这么简单。
> **目录已分离**：`methodology\`（跨任务复用）与 `task-<任务名>\`（本次任务专属）**互不污染**；
> 任务目录**不随本包分发**，用包里的三份模板在 `methodology\` 同级新建（见 `methodology\_先读这份-READ-FIRST.md` §三.1）。

## 一、这个包里有什么

```
蓝图规范-共享版\
├── methodology\                      ★ 方法论：给 AI，整个文件夹直接投喂，不用拆
│   ├── _先读这份-READ-FIRST.md             读取指令：按角色给最小必读集 + 任务目录怎么建
│   ├── BLUEPRINT-撰写规范.md               规范本体：蓝图 12 节 / 完成报告 10 节 / 判据台账 / 回写
│   ├── BLUEPRINT-回写规范与清单模板.md        T1–T4 触发条件 + 四列回写清单模板
│   ├── BLUEPRINT-经验库.md                  ★唯一经验库：P/B/V/C/R/H/I 七类，111 条、约 2 万字符，写蓝图前通读一次
│   ├── BLUEPRINT-经验库-全量台账.md          旧版 186 条 R + 22 条 X，带出处标识（**只用于考古**，日常不读）
│   └── 模板-总蓝图.md · 模板-施工蓝图.md · 模板-完成报告.md    三份可直接抄的骨架
│
├── README.md                        ← 你正在读的这份（给人读；**文件名就是 `README.md`**，GitHub 会直接渲染）
├── 投喂说明-先读我.md                 可直接复制粘贴给 AI 的开场话术（给人读）
├── CHANGELOG-v3.0.md               ← v3.0 改了什么、怎么验的、还剩什么问题
├── CHANGELOG-v3.1.1.md             ← v3.1.1 任务目录大小写修复
├── CHANGELOG-v3.2.md               ← v3.2 基线文件 BASELINE.txt（数字唯一定义点）
├── CHANGELOG-v3.3.md               ← v3.3 并行模式 concurrent/（隔离副本 + AD.md 并入）
├── concurrent\                    并行区（v3.3）：AD.md 并入清单 + 隔离副本；**并行时才有内容**
└── task-NAME\                      占位目录示例（**小写 `task-` 开头**）：把施工蓝图放进这里，或照它的位置建 `task-<任务名>\`
```

**本包有意不含两样东西**：

| 不含什么 | 为什么 | 你要用的时候怎么办 |
|---|---|---|
| **任务目录 `task-<任务名>\`** | 别人的基线与已拍板决策一旦混进来，就会变成你的约束——这是"经验越用越错"的主要来源 | 在 `methodology\` **同级**新建，用三份模板各抄一份（见 `methodology\_先读这份-READ-FIRST.md` §三.1） |
| **经验的原始存档** | 那是 19 万字符级的历史记录，其中九成不需要读 | 不需要：经验条目**自身是完整的**（反例 / 为什么会错 / 怎么才对 三段齐全）；旧版 `文件:行号` 出处已归档进全量台账 |

**各部分的读者与分享方式**：

| 目录 | 给谁 | 分享时 |
|---|---|---|
| **`methodology\`** | AI（也能给人看） | **可以直接单独分享**——它自包含、**不含任何指向包外文件的链接**，拷到任何任务旁边都能用 |
| `README.md` · `投喂说明-先读我.md` | 人 | 建议一起给，尤其是给不熟悉这套方法的人 |

## 二、怎么用（一句话版）

**把 `methodology\` 整个文件夹拖给 AI，然后说**：

```
这个文件夹里是一套写蓝图用的规范与经验库。
请先读 methodology\_先读这份-READ-FIRST.md，按里面的最小必读集决定读哪几份。

读完**先进入审计模式**：不要改代码、不要写蓝图、不要建 task 目录。
分四轮问我（每轮 2–4 个问题）：目标与边界 → 现状与前置 → 验收与风险 → 复述确认。
能自己查的（仓库路径 / 分支 / 未提交改动）先 grep 再问。
四轮走完给我一份「任务理解确认书」，等我说「开始」再写蓝图。
```

> 🔴 **这一句「先进入审计模式」不能省。** 少了它，AI 读完的默认动作是「复述角色 + 列必读集 + 开始写」——
> 而实测里这正是最贵的一次返工的起点：蓝图根基错了，整份作废。
> **审计的成本是几轮对话，不审计的成本是一份蓝图加一次施工。**

AI 会只读该读的 **2–3 份**（约 6.7 万字符；经验库按 §0 六问自检 + §8 场景速查定位），不会去啃另外几份大的。

## 三、四种用法

| 场景 | 给 AI 什么 | 关键点 |
|---|---|---|
| **A 写一份新蓝图** ★最常用 | `methodology\` + 你这个任务自己的背景材料 | 规范给正面结构，经验库给负面清单，两者合起来就够 |
| **B 执行一份已有的蓝图** | 该任务的总蓝图 + 该阶段的蓝图（**就两个**） | **不要给规范和经验库全文**——执行者读得越少越不容易被带偏 |
| **C 迁移到自己的项目** | `methodology\` | 用规范 §1–§10 全部 + 经验库 P/B/V/C/R/H 六类全部 + I 类**只取形状**；I 类条目多为 Node/Electron/PS 场景，**参考形状、别照抄命令结论** |
| **D 查证某条经验** | `methodology\BLUEPRINT-经验库-全量台账.md` | 约 **6 万 token**，**用关键词定位，别整份读** |

**场景 A 的完整话术**：

```
你现在的任务是【写蓝图】，不是执行。

输入：
1. methodology\BLUEPRINT-撰写规范.md —— 写作规范，你的蓝图必须满足它的 §4（12 节结构）
2. methodology\BLUEPRINT-经验库.md —— 唯一经验库（约 2 万字符 / 111 条），写之前通读一次；先看 §0 六问自检
4. <你这个任务的总蓝图>
5. <当前阶段文档 / 上一份完成报告>（至少读它的「五、关键偏差」与「十、回写清单」）

请产出「阶段 N 施工蓝图」，要求：
- 严格按撰写规范 §4 的 12 节结构
- 「非目标」逐条给"为什么不做"
- 「实测证据」一节写：支撑决策的实测数字，以及**被推翻的原计划**
- 每条验收判据要能判定，并写明失败处置；区分「充分判据」与「启发式指标」
- 写完自检：经验库 §0 的六问自检逐问一遍，本蓝图有没有踩
```

**场景 B 的完整话术**：

```
你现在的任务是【执行阶段 N】，不是写文档。

输入：
1. <该任务的总蓝图> —— 全局约束与已拍板决策（不得重新论证）
2. <PHASE-N 蓝图> —— 本阶段的施工蓝图，自包含

要求：
- 先核对蓝图第 3 节的「前置条件」（含"上阶段回写清单无未勾选项"），不满足就停下报告
- 遇到真实代码与蓝图冲突时，**以真实代码为准**，并记录下来
- 出现第 3 节的「停止条件」时立即停止并报告，不要自行绕过
- 执行完毕产出「完成报告」，10 节结构：
  执行摘要 / 最终状态 / 执行过程 / 验收逐项结果 / 关键偏差与判定修正 /
  已知坑复现情况 / 回退方法 / 交接清单 / 目标达成核对 / **回写清单（未勾完不得提交）**
```

## 四、两个 agent 读的不是同一批文件（最容易搞混）

| 角色 | 读什么 | 产出 |
|---|---|---|
| **撰写者**（写蓝图的 agent，就是你） | 撰写规范 + 经验库 + 该任务总蓝图 + 上阶段报告的「关键偏差」与「回写清单」 | 下一份 **阶段蓝图** + 复核补正 + 回写 |
| **执行者**（另一个 agent，读你的蓝图） | **只要两份**：总蓝图 + 当前阶段蓝图（**不读**规范全文、**不读**经验库） | 代码改动 + **完成报告** + 施工记录 |

**三句话记住分工**：

1. **撰写者写蓝图，不施工。** 一旦动手改代码，后面那节「独立复核」就失去意义——自己检查自己等于没检查。
2. **执行者只读两份**（总蓝图 + 当前阶段蓝图），**没有你的对话历史**。所以你写漏一步，他就漏做一步——**蓝图必须自包含**。
3. **两人都是 agent，都不替代人。** 产品取向、真实渠道验证（QQ / 真机 / 支付）永远是人的事，见人工台账的 `M` 档。

## 五、这套体系的三个机制（v2.2 新增，最重要）

### 5.1 方法论与任务分离

```
methodology\      跨任务复用 —— 整体拷到另一个任务旁边，无需改动即可用
task-<任务名>\    任务专属 —— 总蓝图 / 阶段蓝图 / 报告 / 决策 / 人工台账（**各任务自建**，见 §一）
```

**为什么**：混在一起时，新任务的 agent 会读到**上一个任务的基线数值与已拍板决策**，
把别人的结论当自己的约束——这是"经验越用越错"的主要来源。
**跨目录引用一律用相对路径**（`../methodology/…`），不许写裸文件名。

### 5.2 经验库的组织（**七类**）

| 等级 | 判据（自评问句） | 放哪 | 读法 |
|---|---|---|---|
| **P** 判据 | 这条验收能不能证明我想证明的事 | 经验库 §1 | 写判据时对照 |
| **B** 边界 | 一个语义在系统里有几处载体 | 经验库 §2 | 改结构 / 删东西时对照 |
| **V** 验证 | 尺子 / 对照物 / 数据源可不可信 | 经验库 §3 | 做核验时对照 |
| **C** 变更 | 顺序 / 传播面 / 不可逆 | 经验库 §4 | 施工前对照 |
| **R** 报告 | 数字与产物怎么留痕 | 经验库 §5 | 写报告时对照 |
| **H** 人在环 | 哪些必须人做 | 经验库 §6 | 排验收时对照 |
| **I** 基础设施 | 命令与工具的行为坑（L 级） | 经验库 §7 | **换栈必须重新实测** |

**避免的错**：把 **I 类**（基础设施）的具体结论当通用知识套用——那些命令与 API 结论只在那套技术栈成立，换栈要重新实测。

**为什么不再分 H/M/L 三库**：旧版按迁移性拆成「通用 / 具体坑 / 全量台账」三份、共 33 万字符，
设计前提是「按角色取最小必读集」。实测结论是——**agent 在任务中途不会回头翻库**，
于是库越大越全，换来的是上下文被吃掉一半、实际读到的条数接近 0。
现在按**失效类别**组织成一份约 2 万字符的库：容量换可读性，通读一次的成本远低于它拦下的返工。

### 5.3 修正回写（**修正不能只活在报告里**）

| 触发 | 回写目标 |
|---|---|
| **T1** 判据被修正 | 判据台账（总蓝图 §9.1 / 规范 §7.2） |
| **T2** 基线数值被改写 | **`task-<任务名>/BASELINE.txt`**（不是总蓝图 §九）；旧值移入总蓝图 **§9.2 历史基线** |
| **T3** 蓝图描述被实测推翻 | 总蓝图对应节；保留「**曾错、已修正**」说明 |
| **T4** 新增一条经验 | `BLUEPRINT-经验库.md`，按失效类别归入 P/B/V/C/R/H/I 某节 |

- 完成报告末尾必须有「**回写清单**」四列表：触发条件 / 回写目标 / 回写内容 / 已勾选，
  **未勾选完不得提交**。
- 下一阶段前置条件含两条：**上阶段回写清单无未勾选项** + **台账无未闭合的 H-A 与 M 档项**。
  检查命令见规范 §5.1（**唯一定义处**），且必须配一次**负向对照**——拿一份故意留 `[ ]` 的样例跑，**必须命中**。
- **回写只「新增 + 标注」，不静默删除。**
- 🔴 **检查"有没有漏勾"不能全文搜 `[ ]`** —— 那一行判据自己就含这个标记；要限定作用域（`^\|.*\[ \]`）或改成结构判据。

### 5.4 双角色复核（v2.4 新增，来自一次真实合并）

**写蓝图的人**与**执行蓝图的人**是两个 agent；每个 Phase 交付后，**撰写者独立复核**并追加一节
「**撰写者复核补正**」到完成报告（规范 §5.2）。要点：

- **不采信报告自述**：逐条独立复跑；关键判据**用与执行者不同的机制重写**（机制不同 ⇒ 互为交叉验证）。
- **四步归因法**：出"红"时先走完 (a) 改动面是否为空 → (b) 隔离复现 → (c) 机制命中（`stderr` 字节数吻合）→ (d) 修环境后转绿，**再定性**。
- **它买到什么**：拦下"两个口径相减"的假警报、把"数行数"升级成"比哈希"、区分"数字不可复现"与"结论错误"、
  让"无功能影响"第一次有证据、把"全绿"从"判执行者对错"改成"**判判据缺前提**"。
- **结项 Phase 也必须复核**（实测最需要外部复核的，恰是执行者自己改台账的那一 Phase）。

配套的两类文档（规范 §4.1 / §5.3）：**人工验证台账**（人工验证的**唯一载体**——一个环节一行，
agent 预填「要验什么 / 期望值 / 证据」，人只填后三列，**验完就地回填、不新建文件**；v2.4.1）·
**缺陷报告**（安全 / 隐私 / 数据类缺陷单独立项，不塞进"小修"）。

## 六、经验条目的「出处」怎么读（分享场景必读）

条目末尾的「出处」是**原始记录的文档标识 + 行号**，两种形态：

```
① SELF-update 260925/phase3-p3-erasure-and-console.md:1622-1646   ← 8 份施工记录之一
② task-仓库合并/PHASE-2-完成报告.md:44                             ← 一次真实任务的完成报告
```

1. 它标识"**这条经验当时从哪份记录的哪几行抽出来**"，用于**溯源**；
   键号（C7 / D13 / R140…）本身也承担**唯一标识**，可被蓝图与报告直接交叉引用。
2. **这两类原始文档都不随本包分发**——所以出处**不是**包内的可打开路径，也不要去本包里找它。
3. **不解析出处完全不影响使用**：经验的价值**写在条目里**（错误做法 / 症状 / 根因 / 正确做法四段完整）。
4. 本包内**所有**跨目录引用都是相对路径（`methodology/…`、`../task-<任务名>/…`），任务侧一律是占位符，
   **不含指向包外文件的链接**——`methodology\` 可直接转发。
   ⚠️ **例外**：少数「环境类」条目会引用**原机器的绝对路径**（如 `D:\data\node24\npx.cmd`、`D:\data\node\npm.cmd`），
   那是**历史记录的原文**，用来描述当时那台机器的环境——**当举例看，不要照抄执行**，换成你自己的路径即可。

## 七、常见误用

| 误用 | 后果 | 正确做法 |
|---|---|---|
| 让 AI 通读 `methodology\` 全部 8 份 | 约 **18.7 万字符**，大半本轮用不上 | 按 `methodology\_先读这份-READ-FIRST.md` 的**最小必读集**读 2–3 份 |
| 把规范喂给**执行**者 | 执行者去纠结文档结构而不干活 | 只给总蓝图 + 阶段蓝图 |
| 写蓝图时不给上一份完成报告 | 重复踩已经踩过的坑 | 至少给上阶段报告的「关键偏差」+「回写清单」 |
| 只把文件夹丢过去、一句话不说 | AI 可能把"规范"当成"要执行的任务" | 用第二节 / 第三节的话术 |
| 拿 L 级经验的具体结论套别的技术栈 | 误伤无关代码 | 用**形状**自检，别照抄结论；L 级只在同栈复用 |
| 在本包里翻找"范例任务"或"证据存档" | 翻不到，白花时间，还可能误以为包是残缺的 | 任务目录自己建（§三.1）；**出处只是记录标识**，不是可打开的路径 |
| 把某个任务的总蓝图当模板复用给新任务 | 别人的基线与决策变成你的约束 | 换任务时用 `methodology\模板-总蓝图.md` 重写；只有 `methodology\` 才复用 |
| 修正只写进完成报告 | 后续阶段得翻遍旧报告才知道按哪版执行 | 按 T1–T4 **回写**，清单未勾完不提交 |

## 八、这是快照：怎么判断是否过期

**本包是某一时刻的快照，上游仍在演进。** 实测：本包生成前后 20 分钟内，
规范就从 v2.0 走到了 v2.1（蓝图 11 节 → 12 节、新增「人工环节」），某阶段文档从 501 行重写到 1054 行。

| 检查点 | 本快照的值 |
|---|---|
| 规范版本号（文件抬头 `> **版本**`） | **v3.3** |
| 施工蓝图必备结构 | **12 节**（含「五、人工环节」，功能清单带 `档` 列） |
| 完成报告必备结构 | **10 节 + 三个追加节（十一 / 十二 / 十三，编号连续不跳号）** |

## 九、来源

- 规范与经验库的形态提炼自一套真实的多阶段施工记录（约 8800 行、8 份文档，**未随本包分发**）；
  经验条目里的 `SELF-update 260925\…` 就是那批文档的标识。
- 经验的抽取口径、类型分布、"最珍贵的 10 条"见 `methodology\BLUEPRINT-经验库-全量台账.md` 的附录 A–D。
- 规范 **v3.0** 来自**作者本人的实测反馈与自查**：
  ① **「agent 在任务中途不会回头翻库」** —— 三份经验库合计 19.5 万字符，实际读到的常为 0；
     于是收敛为单库（2 万字符 / 106 条），组织方式由「按迁移性 H/M/L」改为「按失效类别 P/B/V/C/R/H/I」。
  ② **「一刀切人工验收会把吞吐锁死」** —— 真实使用中会诱发台账糊弄，比没有台账更糟；
     于是按「机器能不能自己判定」拆成 **M 必验 / O 选验** 两档，默认 O。
  ③ **三处「规范自己踩中自己条目」**：回写门禁命令假绿（P20 判据自命中）、台账列数与归属矛盾（R1 计数无单一出处）、
     完成报告编号跳号（R2 追加吃行）。三处均已修复并配了可复跑的自检。
- 规范 v2.1 新增的「人工环节」（H-A 阻塞拍板 / H-B 完工评审 / H-C 待验登记）见规范 §4.1。
- 规范 v2.2 新增的「目录分离 / 经验分级 / 修正回写」三项机制，见规范 §3.3、§5.1、§9 与
  `methodology\BLUEPRINT-回写规范与清单模板.md`。
- 规范 v2.3 的**断链清理**与新增的 `methodology\模板-总蓝图.md`，见规范 §10 修订台账。

  ① **Phase 严格串行推进**：任意时刻只能存在一个施工态 Phase，严禁提前生成后续 Phase 施工蓝图，必须走完生成门禁（v2.6 当时为 G1–G7，v3.2 已升为十项出口条件）；
